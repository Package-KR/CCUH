# CCUH 첫 보완 후보와 검증 계획

작성일: 2026-11-17 (Asia/Seoul)

상태: 사용자 실제 요구를 반영해 우선순위를 변경했다. 현재 첫 검증 대상은 [대상 화면 제한과 사용자 포커스 보존](target-scope-and-focus.md)이다. 이 문서의 무진전 반복 실험은 후순위 후보로 보관하며, 아직 실행하지 않았다.

## 결정

첫 후보는 **목표 상태가 바뀌지 않았는데 의미가 같은 UI 행동을 반복하는 문제**다. CCUH는 기존 Computer Use의 복구 원칙에 목표 중심 진행 판정과 반복 상한을 더한다.

이것은 문서 분석에서 고른 검증 가설이다. 현재 기본 Computer Use에서 이 문제가 실제로 발생했다거나, CCUH가 개선했다고 판정한 것은 아니다. 이번 작업에서는 원문 분석과 실험 설계까지만 수행했다. 테스트 앱, 스킬 설치, 실제 A/B/C 실행은 아직 하지 않았다.

## 3. CCUH가 보완할 문제 하나

예시: 로컬 자료의 미리보기를 열도록 요청했다. 도구 호출은 성공했고 상태도 다시 읽었지만, 여전히 이전 자료가 보인다. 에이전트가 같은 자료의 같은 열기 동작을 여러 번 반복하면서 목표에 도달하지 못한다.

### 진행과 반복의 정의

- 행동 식별자는 `의미상 대상 + 동작 + 기대한 상태 변화`로 묶는다. 요소 번호나 좌표가 달라져도 같은 자료의 같은 열기를 반복했다면 같은 행동이다.
- 진전은 목표에 관련된 변화다. 대상 자료 ID, 선택 상태, 입력값, 미리보기 내용, 완료 표시 등이 근거다. 시각·커서·무관한 알림 변화는 진전으로 세지 않는다.
- 로딩 표시처럼 완료가 진행 중이라는 증거는 별도로 분류한다. 단순히 다음 관찰에서 완료되지 않았다고 실패로 세지 않는다.
- 값이 증가하는 스피너처럼 같은 동작을 반복해야 목표에 도달하는 경우, 값이 목표 쪽으로 변했다면 진전이다.
- API가 예외 없이 반환했다는 사실은 목표 달성 증거가 아니다.

### 시험할 보완 절차

1. 행동 전에 현재 하위 목표와 기대한 UI 변화 하나를 정한다. 매번 사용자에게 설명할 필요는 없다.
2. 기존 Computer Use 방식으로 행동하고 최신 상태에서 기대 변화가 있었는지 확인한다.
3. 첫 무진전이면 필요한 근거를 추가로 확인한다. 로딩 중이라면 제공된 로딩·대기 기능을 따른다. 동일 AX 재조회와 임의 sleep으로 폴링하지 않는다.
4. 재시도가 타당하고 안전할 때만 같은 행동을 한 번 더 시도한다. 중복 실행의 결과가 불확실하면 재시도하지 않는다.
5. 같은 행동에서 진전 없는 결과가 두 번 확인되면 추가 동일 시도를 멈춘다. 현재 UI 근거에 맞는 다른 방법으로 전환한다. 예: 포커스 재설정, 다른 노출된 열기 경로, 근거 있는 화면 갱신, 지원되는 경우 AX에서 화면 기반 조작으로 전환.
6. 이 하위 목표에는 다른 복구 방법을 최대 두 개까지 시도한다. 방식이 바뀌었다는 이유만으로 예산을 무한 초기화하지 않는다. 목표 관련 진전이 확인되면 해당 실패 계수를 초기화한다.
7. 복구 후에도 불가능하면, 마지막으로 확인한 상태와 시도한 방법을 근거로 구체적 장애 요인을 보고한다. 완료는 목표 상태가 확인된 경우에만 선언한다.

‘동일 행동 두 번’과 ‘복구 방법 두 개’는 실험용 초기값이다. 검증된 최적값이 아니며 다른 기준으로 바꾸면 새 실험 버전으로 취급한다.

## 4. 지원 방식

첫 구현은 API 이름을 고정하지 않은 짧은 보완 Skill로 한다. 목표 판정·반복 예산·복구 선택만 기술하고, 조작 API와 기본 관찰 절차는 현재 환경의 공식 Computer Use 지침을 따른다. @oai/sky 예제를 현재 cua_repl 세션에 그대로 이식하지 않는다.

효과 검증 단계에서는 명시 호출한다. 자동 발견·자동 선택 여부는 별도 실험으로 남긴다. 일반 Markdown 참고 문서가 실제로 읽혔다고 가정하지 않는다. 스킬 본문 접근과 명시 호출 경로를 실행 추적으로 확인한다. 로드되지 않은 시도도 누락하지 않고 적용 실패로 별도 기록한다.

스킬 문장은 실행 강제 장치가 아니다. 초기에는 hooks, MCP 프록시, 공식 스킬 파일 수정 없이 행동 지침의 효과부터 분리해서 본다. 독립 평가 로그를 남기는 코드는 테스트 앱 측에 둔다.

공식 문서에서 스킬은 명시 호출 또는 description에 따른 자동 선택으로 사용되며 선택 시 본문이 로드된다. [Build skills](https://learn.chatgpt.com/docs/build-skills)

## 5. 효과를 검증할 실험

### 평가 환경

더미 자료만 다루는 작은 macOS 네이티브 테스트 앱을 만든다. 실제 앱의 UI를 사용하는 Computer Use 경로를 평가한다. 웹페이지로 대체하면 브라우저 도구 경로를 별도 실험으로 구분한다.

에이전트는 화면과 AX 정보로만 과제를 수행한다. 테스트 앱 소스, 내부 상태, 장애 모드, 정답 로그는 실행 에이전트에게 제공하지 않는다. 평가자는 별도 경로로 최종 상태와 이벤트 로그를 읽는다. 앱 파일, 평가 도구, 정답 로그의 경로를 실행 에이전트가 탐색하는 통로도 막아야 한다. 실제 실행 환경에서 이를 격리할 수 없으면 해당 실험을 유효한 성과 검증으로 인정하지 않는다.

동일 앱에는 정상 UI에도 자연스러운 대체 조작 경로가 있어야 한다. 특정 CCUH 문구를 알아야만 복구되는 퍼즐을 만들지 않는다. 장애는 앱 상태 전이에서 주입한다. 도구 구현을 임의로 패치하거나 모든 오류가 같은 방식으로 복구된다고 가정하지 않는다.

### 세 비교 조건

| 군          | 공식 Computer Use 지침 외 추가 내용                                        |
| ----------- | -------------------------------------------------------------------------- |
| A 기본      | 추가 복구 지침 없음                                                        |
| B 일반 알림 | 같은 동작이 통하지 않으면 반복을 피하고 다른 방법으로 전환하라는 짧은 알림 |
| C CCUH      | 이 문서 3절의 목표 판정·동일 행동 식별·반복 상한·복구 예산 절차            |

B와 C는 같은 명시 호출·파일 로딩 경로를 쓴다. B/C의 길이는 기록하되 무의미한 문장으로 길이를 맞추지 않는다. A에는 추가 복구 지침을 넣지 않는다. B는 일반 알림만으로도 같은 성과를 얻는지 확인하기 위한 비교군이다.

모델과 추론 설정, 앱 빌드, 화면 크기, AX 접근, 런타임/API 경로, 앱 접근 허용 상태, 과제 문구, 초기 데이터, 장애 seed, 시행 예산을 고정한다. 이번 세션처럼 후보 규칙과 복구 정답을 이미 읽은 대화에서 평가하지 않는다. 각 시도는 새 대화·새 REPL·초기화된 앱 상태로 진행하고, 순서는 seed별로 무작위 배정한다. 같은 앱을 여러 에이전트가 동시에 조작하지 않는다.

비교 파일럿은 `6조건 × 3 seed × 3군 = 54회`다. 각 실행의 상한은 3분 또는 UI 변경 행동 30회 중 먼저 도달하는 시점이다. 상태 관찰을 포함한 전체 도구 호출 수도 별도로 기록한다. 시간·행동 상한에 도달하면 평가자가 종료시키고 실패/시간 초과로 남긴다. 평가 상한은 모든 군에 동일하게 적용한다.

그 전에 별도의 선별용 seed 3개로 A만 18회 실행한다. F1/F2 6회에서 목표 진전 없는 동일 행동 3회 이상이 전혀 나타나지 않으면, 이 후보의 필요성이 이번 평가에서 확인되지 않은 것이다. 그때는 비교 파일럿을 진행하기 전에 후보를 보류한다. 재현을 만들기 위해 같은 평가 과제를 계속 조정하지 않는다. 과제나 규칙을 고치면 개발용 자료로 돌리고 새 seed·별도 과제로 평가를 다시 고정한다.

재현 선별에 통과하면 사용하지 않은 seed 3개로 A/B/C 54회를 새로 실행한다. 이 54회 안에서는 seed별 군 순서를 무작위 배정한다. 선별용 A 18회를 비교 파일럿의 A군으로 재사용하지 않는다. 따라서 진행 시 총 72회이며, 18회 선별 결과와 54회 비교 결과를 분리해 보고한다. 선별 단계가 포함되므로 그 자체로 일반적인 실사용 발생 빈도를 추정할 수도 없다.

### 독립 판정과 기록

앱 내부의 상태 전이와 에이전트 실행 추적을 같은 run ID·단조 시각으로 연결한다. UI 클릭만 보고 호출 성공을 추정하지 말고 실행 추적과 앱 상태를 함께 본다. 평가용 상태는 에이전트 화면에 노출하지 않는다.

최소 기록 항목:

- 실행: run ID, 군, 과제 ID, seed, 모델/설정, 앱·지침 해시, 호출 경로, 추가 스킬 로드 여부.
- 사건: 시각, 의미상 대상, 행동 종류, 전후 목표 상태, 로딩 상태, 앱이 실제 적용한 변화.
- 결과: 목표 달성, 잘못된 대상 변경, 무효 반복 수, 첫 무진전부터 복구 전환까지의 행동 수, UI 행동 수, 전체 도구 호출 수, 소요 시간, 사람 개입, 완료/장애/시간 초과 보고.

주된 성과는 **복구 가능한 F1/F2에서의 실제 목표 달성률**이다. 무효 반복 감소는 함께 보는 비용 지표다. 반복을 막아 빨리 포기하면 비용만 좋아질 수 있으므로 이를 단독 성공 기준으로 삼지 않는다.

C1/C2/C3에서는 성공률과 성급한 중단을 확인한다. F3는 완료 과제가 아니므로 목표 달성률의 분모에 넣지 않고, 거짓 완료와 불필요 반복을 별도로 평가한다. 정당한 반복·대기 중 행동과 무효 반복을 구분하는 판정 기준은 실행 전에 고정한다. 앱 로그로 자동 판정하기 어려운 추적은 군 이름을 가린 평가자가 확인한다.

### 채택·보류 기준

이 54회는 후보를 걸러내는 파일럿이며 통계적 효과 입증이나 전체 Computer Use에 대한 일반화가 아니다. 아래는 다음 실험으로 넘어갈 잠정 기준이다.

- 기본 A에서 실제 무진전 반복 문제가 관찰될 것.
- C의 F1/F2 성공 건수가 A와 B보다 낮지 않고, 두 군에 비해 무효 반복이 각각 30% 이상 줄어들 것. 비교군 반복 수가 0이면 감소 효과를 주장하지 않음.
- C1/C2/C3의 성공 건수가 A/B보다 낮아지지 않고, C에서 거짓 완료가 없을 것.
- 앱 동작 오류·로드 실패·사람 개입을 제외해 유리한 결과만 남기지 않을 것. 전체 배정 결과와 지침이 정상 로드된 결과를 함께 제시할 것.

통과하면 스킬과 기준을 고정하고, 개발에 사용하지 않은 별도 과제와 seed로 재검증한다. B와 차이가 없으면 더 짧은 알림으로 충분할 가능성을 우선 검토한다. A가 이미 잘 복구하면 첫 후보를 바꾼다. C가 반복만 줄이고 성공률을 떨어뜨리면 상한 규칙을 채택하지 않는다.

## 6. 다음 구현의 범위

1. 네이티브 테스트 앱과 독립 이벤트 로그를 준비한다.
2. F1/F2의 장애 주입, 대체 UI 경로, C2/C3의 대조 조건을 사람의 수동 조작으로 확인한다.
3. 선별용 A 18회로 문제 재현 여부를 확인한다.
4. 재현되면 B/C 실험 스킬을 같은 로딩 경로로 준비하고, 새 seed에서 A/B/C 54회를 무작위 순서로 실행한다.
5. 성과가 확인된 규칙만 CCUH v0.1에 넣고 자동 적용·배포 방식은 이후에 평가한다.

이번 분석에서 확정한 것은 문제 후보와 반증 가능한 검증 절차다. 효과나 실사용 결함의 존재는 아직 확정하지 않았다.
