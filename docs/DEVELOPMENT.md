# CCUH 개발 계획

## 목표와 범위

사용자가 Computer Use만 요청해도 CCUH가 자동으로 연결되고, 허용된 대상에서 사용자 작업을 방해하지 않고 실행되어야 합니다.

- 작동 범위는 사용자가 허용한 Computer Use 작업입니다. 일반 코딩, 셸, 검색과 다른 도구에는 작동하지 않습니다.
- 앱 접근 제한과 필요한 승인을 그대로 따릅니다. 창 목록에 나타난 사실이나 도구 이름을 접근 허용의 증거로 사용하지 않습니다.
- 사용자 포커스와 AI의 작업 대상을 구분합니다. 첫 호출과 시험 앱의 시작 및 종료도 검증 범위에 포함합니다.
- 카카오톡과 메모는 시험 예시입니다. 특정 앱이나 대화 상대에 맞춘 제품으로 설계하지 않습니다.
- 모호한 대상, 권한 거부, 참조 만료와 불확실한 동작 결과에서는 중단합니다. 전경 입력으로 전환하거나 전송을 반복하지 않습니다.

## 진행 현황

| ---- | ------ | ------------------------------- | ---------------------------------------------------------------------- |
| 0    | 완료   | 기존 구현 제거와 폴더 구조 유지 | 구현 파일과 산출물 제거, 실행 연결 해제, 개발 계획 정리                |
| 1    | 완료   | 자동 수신                       | 실제 Computer Use 호출이 별도 CCUH 도구 선택 없이 수신기를 실행함      |
| 2    | 미착수 | 앱 접근 제한과 포커스           | 앱 허용과 거부를 따르고 첫 호출부터 사용자 포커스를 유지함             |
| 3    | 미착수 | 대상 발견                       | 허용된 앱과 정확한 창을 읽기 전용으로 식별하며 모호하면 중단함         |
| 4    | 미착수 | 대상 유지                       | 사용자 앱 전환에도 같은 창을 유지하며 닫힌 창에 자동 재연결하지 않음   |
| 5    | 미착수 | 동작 실행                       | 시험 앱의 값 변경과 버튼 동작을 각각 한 번 실행하고 실제 결과를 확인함 |
| 6    | 미착수 | 실패와 수명 관리                | 취소, 시간 초과, 권한 철회와 종료에서 접근과 소유 프로세스가 정리됨    |
| 7    | 미착수 | 통합과 배포                     | 설치된 버전에서 Computer Use 요청 하나로 전체 흐름이 재현됨            |

기존 구현의 검사 결과를 새 단계의 완료 증거로 옮기지 않습니다. 현재 완료한 기능은 최소 수신기의 자동 실행뿐입니다.

## 1. 자동 수신

현재 사용자가 요청한 작업은 **실제 Computer Use 호출이 수신기를 자동 실행하는지**만 확인하는 것입니다. 앱 조회, 창 조작, 입력과 네이티브 엔진은 구현하지 않았습니다.

공식 PreToolUse 명령 훅 하나가 `hooks/receiver.mjs`를 통해 `src/hooks/receiver.ts`를 실행합니다. MCP 서버나 별도의 CCUH 도구 선택은 필요하지 않습니다. 이 연결은 이후의 UI 실행 경로를 확정하지 않습니다.

훅 매처와 수신기의 조건은 두 정확한 도구명을 필터링합니다. 호출자를 인증하는 검사는 아니므로 같은 형식의 입력을 수동으로 전달해도 기록이 생길 수 있습니다. 현재 구현은 다른 경로에서의 직접 실행이나 위조 입력을 절대 차단하지 않습니다. 수신 파일의 존재만으로 자동 호출을 증명하지 않고, 실제 Codex 호출의 코드 해시와 시각 및 수신기 소스 해시를 대조합니다.

### 실제 검증 결과

| 항목        | 결과                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------- |
| 첫 호출 A   | 실제 도구 호출은 실행됐으나 수신 기록 없음. 공식 hooks/list에서 새 훅의 `trustStatus: modified` 확인 |
| 사용자 조치 | Codex App에서 수신기 PreToolUse 한 항목을 직접 검토하고 신뢰 승인                                    |
| 실제 호출 B | `nodeRepl.write("CCUH_STAGE1_LIVE_20261102_B");` 실행. 별도 CCUH MCP 호출이나 수신기 직접 실행 없음  |
| 수신 증거   | 2026-11-01T15:29:19.387Z에 새 수신 기록 생성. receiptId: `be09fcdf-afbb-4baa-9a4d-fe8d8b02da3b`      |
| 대조        | 실제 호출의 코드 해시 및 설치된 수신기의 소스 해시 모두 일치                                         |
| 제외 확인   | 이후 일반 `exec_command` 실행에서 수신 기록 변경 없음                                                |
| 판정        | **Computer Use의 js 호출이 수신기를 자동 실행하는 경로 통과**                                        |

수신 증거는 `~/.codex/ccuh/receiver/last-receipt.json` 한 건만 보관합니다. 수신 시각, 호출과 세션 및 코드의 해시, 수신기 소스 해시만 기록하며 코드와 UI 본문은 저장하지 않습니다.

타입 검사와 격리된 합성 입력 검사도 통과했습니다. 합성 입력에서는 지원 도구명 필터, 크기 제한, 무출력과 원문 폐기를 확인했으며 이 결과를 실제 자동 실행의 증거로 계산하지 않았습니다. `js_reset`은 필터에 포함되지만 실제 reset 호출은 이번에 검증하지 않았습니다.

이 단계는 수신만 확인합니다. 앱 접근 허용의 증명, 창 대상 확인과 실제 UI 작업에서의 포커스 보존은 검증하지 않았으며 다음 단계를 자동으로 진행하지 않습니다.

### 리팩토링의 검증 범위

입력 읽기, 이벤트 검증과 변환, 증거 구성과 파일 저장을 같은 수신기 파일 안에서 분리했습니다. 훅의 도구명 매처, 수신 형식과 기록 항목은 유지합니다. 위 실제 호출 B와 이후 재확인 C는 소스 해시 `3951c348024cdf2c1355e2fcf7af57b7fb3419fbf09df5ed95f49765e7c68f4f`의 설치본에서 확인한 결과입니다. 리팩토링한 저장소 소스의 동등성은 격리된 입력 검사와 타입 검사로 확인하며, 설치본 갱신과 새 소스의 실제 자동 호출 재검증은 이번 변경에 포함하지 않습니다.

리팩토링 후 타입 검사와 23개 입력의 전후 동등성 검사를 통과했습니다. 정확한 도구명 매칭, 기록 내용, 원문 폐기, 저장 실패 처리와 파일 권한을 함께 확인했습니다. 검사는 임시 경로에서 수행하고 제거했으며 실제 수신 기록은 변경하지 않았습니다.

## 2. 앱 접근 제한과 포커스

이 단계는 아직 시작하지 않았습니다. 창 탐색기와 입력 엔진을 만들기 전에 아래 조건을 같은 실제 경로에서 확인합니다.

1. 공식 앱 접근 허용과 거부를 구별할 수 있는 증거를 확인합니다. 성공한 임의 JS 호출이나 앱 목록을 앱 승인으로 해석하지 않습니다.
2. 허용된 요청 뒤의 읽기 전용 시험 작업에서 자동 연결을 확인합니다. 거부된 요청에서는 네이티브 접근이 없어야 합니다.
3. 시험 앱 시작 전부터 종료 후까지 전경 앱과 실제 입력 대상의 변화를 별도로 관측합니다. 시작 시의 잠깐의 활성화도 실패로 기록합니다.
4. 오류, 시간 초과와 연결 끊김에서 기존 호출이 계속되는지 확인합니다. 훅의 실패 처리만으로 포커스 보존을 보장한다고 추정하지 않습니다.
5. 일반 코딩과 다른 도구 호출에서는 CCUH의 UI 접근이 없어야 합니다.

**진행 조건:** 자동 호출, 앱 제한과 첫 호출부터의 포커스 유지가 같은 실제 경로에서 모두 확인되어야 합니다. 하나라도 확인할 수 없으면 원인과 필요한 호스트 기능을 정리하고 연결 설계를 다시 선택합니다. 뒤 단계의 기능으로 이 문제를 덮지 않습니다.

## 3. 대상 발견

허용된 앱의 창 제목, 앱 식별자와 창 식별자를 읽기만 합니다. 전경 앱은 작업 대상의 기본값으로 사용하지 않습니다.

유일한 대상, 같은 제목의 여러 창, 다른 데스크탑과 전체화면 뒤의 창을 구별합니다. 부분 목록은 전체 목록처럼 취급하지 않고, 모호하거나 권한이 없으면 중단합니다.

**진행 조건:** 식별 결과와 실제 창을 대조한 증거가 있으며, 발견 과정에서 앱 활성화나 입력이 없어야 합니다.

## 4. 대상 유지

확보한 창 참조를 작업에 묶고, 사용자 포커스 변경으로 다시 선택하지 않습니다.

재조회는 사용자가 요청한 작업을 이어갈 때, 대상 상태가 바뀌었을 때, 관측 결과가 예상과 다를 때 수행합니다. 같은 실패를 조건 변화 없이 반복하거나 상시 폴링하지 않습니다. 창 닫기, 앱 종료와 식별자 재사용 시 기존 참조를 무효화합니다.

**진행 조건:** 사용자 앱 전환, 데스크탑 전환, 전체화면, 최소화와 복원에서 참조 처리 결과가 명확해야 합니다. 닫았다가 다시 연 창은 명시적으로 새 대상을 확보해야 합니다.

## 5. 동작 실행

자체 시험 앱에서 값 변경 한 번과 버튼 실행 한 번부터 확인합니다. 입력할 값, 대상 요소, 실행 전 상태와 기대 결과를 명시합니다.

실제 변경 결과와 실행 횟수를 독립적으로 확인합니다. 보안 입력란, 비활성 요소, 오래된 참조와 다른 창의 요소는 차단합니다. 불확실한 전송이나 저장은 자동 재시도하지 않습니다.

**진행 조건:** 올바른 대상의 결과와 단일 실행이 확인되고 사용자 작업에 영향이 없어야 합니다. 요소 변화만 확인한 경우 메시지 전달이나 저장 완료까지 확인했다고 하지 않습니다.

## 6. 실패와 수명 관리

취소, 시간 초과, 연결 끊김, 앱 종료, 접근 권한 철회와 재시작을 검증합니다. 작업이 끝나면 소유한 세션, 관측기와 하위 프로세스를 정리합니다.

**진행 조건:** 실패한 작업을 성공으로 보고하지 않으며, 권한이 사라진 뒤의 접근과 자동 중복 실행이 없어야 합니다. 정리 동작도 사용자의 화면과 포커스를 바꾸지 않아야 합니다.

## 7. 통합과 배포

Computer Use만 요청한 새 작업에서 허용, 거부, 잘못된 대상과 동작 실패를 검증합니다. 사용자나 모델이 CCUH 도구를 별도로 고르는 과정을 자동 연결로 보고하지 않습니다.

배포 패키지는 검증한 실행 경로를 사용해야 합니다. Codex App과 CLI는 각각 검증하고, 설치와 훅 신뢰 승인을 구분합니다. 이 단계에서 패키지 명령, CI와 릴리스를 다시 연결합니다.

**진행 조건:** 실제 설치본의 코드 식별과 전 과정 결과가 개발본의 검증 근거와 일치해야 합니다.

## 작업 단위와 기록

한 번에 한 단계의 한 가지 가설을 다룹니다. 단계마다 아래 항목을 이 문서에 기록하며, 독립적인 진행표를 늘리지 않습니다.

| 항목      | 기록할 내용                           |
| --------- | ------------------------------------- |
| 가설      | 이번에 무엇을 확인하려는지            |
| 범위      | 변경할 계층과 허용된 작업             |
| 판정 기준 | 성공과 실패를 구분할 관측값           |
| 결과      | 통과, 실패, 미확인과 실제 근거        |
| 다음 행동 | 현재 단계를 계속할지 다음 단계로 갈지 |

재현과 검증은 가능한 범위에서 자동화합니다. 사람의 동시 작업처럼 자동 관측으로 확인할 수 없는 항목만 사용자에게 요청하며, 필요한 이유와 한 가지 행동을 명확히 설명합니다. 검사 개수만으로 기능 완료를 판단하지 않습니다.

## 폴더 사용 원칙

기존 아키텍처 폴더는 유지합니다. 각 단계에서 책임이 생길 때 필요한 최소 파일만 추가합니다. 아직 선택하지 않은 연결 방식이나 엔진을 위한 추상화, 설치기와 배포 코드를 미리 만들지 않습니다.

현재 저장소에는 최소 훅 수신기만 있습니다. 창 탐색, 앱 조작, MCP 서버와 네이티브 엔진은 없으며 CI와 공개 릴리스는 중단한 상태입니다.
