# CCUH 개발 체크리스트

## 목적과 범위

Computer Use가 작업할 앱을 인식하는 부분과, 인식한 앱 안에서 입력이나 클릭 등의 작업이 실패하는 부분을 보완합니다.

기존 자동 수신은 연결 기반으로 유지합니다. 실제 보완 기능은 앱 인식 문제와 앱 내부 작업 실패에 집중하며, 일반적인 전체화면이나 모니터 배치 시험을 별도 개발 단계로 늘리지 않습니다.

## 도메인 구조

| 도메인   | 폴더               | 책임                                                            |
| -------- | ------------------ | --------------------------------------------------------------- |
| 공통     | `src/common/`      | Computer Use 연결, 호출과 결과 연결, 공통 오류 형식과 최소 로그 |
| 인식     | `src/recognition/` | 의도한 앱과 창 식별, 잘못된 대상과 오래된 참조 처리             |
| 내부처리 | `src/interaction/` | 앱 내부 입력과 클릭 등의 실패 확인, 결과 검증과 안전한 재시도   |

현재 구현은 `src/common/hooks/receiver.ts`의 호출 전후 수신기입니다. 인식과 내부처리 폴더는 아직 구현 자리이며, 앱 인식이나 오류 복구 기능이 완성됐다는 뜻은 아닙니다.

### 1.3 검증 기록

2026-11-02 Codex App에서 두 훅이 `trusted`인 상태로 확인했습니다. 공통 수신기와 두 진입점, 훅 설정은 로컬 설치본과 일치하며, 검증 소스 해시는 `55d9ecf6a4cb32054ab016999f41f270792f9e6caed3c72cffc9b4f86ed07cad`입니다.

| 실제 Computer Use 호출            | 관측 결과                                                                                 |
| --------------------------------- | ----------------------------------------------------------------------------------------- |
| 정상 `js` 반환                    | 호출 전후 세션, 호출과 코드 해시 일치, `isError: false`                                   |
| JS 내부에서 오류를 잡고 정상 반환 | 호출 전후 일치, `isError: false`. 내부 실패를 이 플래그로 알아낼 수 없음                  |
| JS 오류 던지기                    | 호출 전 기록만 새로 생성. 호출 후 기록은 앞선 호출의 값이므로 이번 반환으로 연결하지 않음 |
| `js_reset`                        | 호출 전후 일치, 코드 해시 `null`, `isError: false`                                        |

별도 임시 저장소에서 훅 프로세스 35회를 실행했습니다. 응답 누락과 `null`, `false`, `0`, 빈 문자열, 배열과 객체를 구분했으며, 오류 플래그의 잘못된 자료형은 미확인으로 남았습니다. 표준 콘텐츠와 미지원 유형, 원문 비저장, 단계와 도구명 불일치, 교차 완료 호출, 입력 상한 전후, 저장 오류와 파일 권한을 확인했습니다. 임시 검사는 실제 자동 수신 근거와 구분합니다.

실제 비대상 코드 실행, 파일 수정, 검색과 다른 MCP 호출 뒤에도 최신 시작 표식, 호출과 반환 기록의 식별자가 모두 유지됐습니다. 이 관측 구간의 기록 비교이며 OS 프로세스 생성 전체를 감사한 결과는 아닙니다. 타입, 두 진입점 문법, 포맷과 릴리스 메타데이터 검사도 통과했습니다.

### 관측 한계

- `last-start.json`, `last-receipt.json`, `last-result.json`은 각각 최신 기록입니다. 서로 인접한 파일이라고 같은 호출은 아니며 세션과 호출 해시가 일치해야 합니다. 동시 호출 전체 이력은 보존하지 않습니다.
- `isError: false`는 도구 반환에 실린 값입니다. 올바른 앱 인식, 입력, 클릭, 저장이나 전송의 성공 증거가 아닙니다. 오류 플래그가 없거나 boolean이 아니면 `null`로 기록합니다.
- 이번 설치 환경의 오류 던지기 시험에서는 해당 호출의 호출 후 훅 수신이 관측되지 않았습니다. 반환 기록 부재만으로 오류, 취소, 시간 초과나 서버 종료 중 어느 원인인지 단정하지 않습니다. 확인한 설치 버전의 공식 훅 이벤트 목록에는 별도 도구 실패 이벤트가 없습니다.
- 호출 전 입력은 256 KiB, 호출 후 입력은 8 MiB까지 읽어 해석합니다. 호출 후 상한을 넘으면 `input_limit_exceeded`만 기록하고 호출 및 응답 정보는 미확인으로 둡니다. 원래 응답은 바꾸지 않으며 오류 본문이나 화면 내용은 저장하지 않습니다.
- 최신 상태 파일은 원자적으로 교체합니다. 쓰기 도중 프로세스가 강제 종료되면 `.pending` 파일이 남을 수 있습니다.
- 이름이 일치하는 공유 CUA 호출만 수신하지만, 도구 이름은 사용자 플러그인 선택의 인증이나 앱 접근 승인이 아닙니다. 앱 승인과 실제 UI 결과는 이후 단계에서 별도로 확인합니다.

## 2. 인식

- [x] **2.1 인식 문제 재현** — 같은 앱의 다른 창을 선택하면 기존 공식 `App` 객체의 최신 관측도 그 창으로 바뀌어 작업 의도와 달라지는 사례를 실제 Computer Use에서 재현했습니다. 앱 연결과 특정 창의 고정 참조를 구분합니다.
- [ ] **2.2 인식 실패 구분** — 앱을 찾지 못함, 다른 앱이나 창 연결, 오래된 참조와 접근 거부를 실제 근거로 구분합니다. 구분할 수 없으면 원인 미확인으로 남깁니다.
- [ ] **2.3 대상 재확인과 복구** — 허용된 대상의 새 상태나 참조를 확보한 뒤 올바른 연결인지 검증합니다. 새 정보 없이 같은 선택을 반복하지 않습니다.

### 2.1 검증 기록

2026-11-02 14:21 KST에 실행 중인 카카오톡의 기존 두 대화창으로 확인했습니다. 이 문서에는 실제 창 제목 대신 의도한 창을 A, 다른 창을 B로 표기합니다. 공식 `cua.getApp('com.kakao.KakaoTalkMac')`으로 받은 앱 객체와 그 객체의 `getAXState()`만으로 대상을 읽고, 앱 안의 채팅 목록과 창 메뉴로 선택했습니다.

| 순서 | 작업                                               | 실제 관측                                    |
| ---- | -------------------------------------------------- | -------------------------------------------- |
| 1    | 첫 앱 객체에서 창 A 선택                           | 최신 상태의 창 제목이 A                      |
| 2    | 같은 앱을 다시 요청해 받은 별도 객체에서 창 B 선택 | 두 번째 객체의 최신 상태가 B                 |
| 3    | 첫 객체로 최신 상태 재조회                         | 앱 표시명은 같지만 창은 B. 의도한 A와 불일치 |
| 4    | 최신 창 메뉴에서 A를 정확히 찾아 재선택            | 첫 객체의 최신 상태가 A로 돌아옴             |

처음 분리해 관측한 순서를 한 Computer Use 호출에 묶어 재검증했고 같은 결과를 얻었습니다. 재검증 호출의 세션, 호출과 코드 해시는 자동 수신된 호출 전후 기록에서 일치했습니다. 공통 수신기 소스와 로컬 설치본도 1.3에 적은 해시와 일치합니다.

- 호출 해시: `f2bcfee26f878db70c46bf7fc674251a1b4fcc7e20f94a78a290df9a2030e438`
- 코드 해시: `946acd0953bd1bcba64ae42bc641f73c9c852c8dc3eb9e323a5ea6f51ce56d17`
- 호출 후 기록: `response_received`, `isError: false`. 코드가 정상 반환됐어도 중간 관측의 창은 의도와 달랐습니다.
- 메시지 작성과 전송은 하지 않았습니다. 앱의 기존 창을 선택하고 읽는 동작만 수행했습니다.

### 확인한 원인과 다음 구현 경계

`App` 객체는 앱에 대한 연결이며 이번 관측에서 특정 창을 고정하지 않았습니다. 다른 창을 선택한 뒤에도 기존 객체를 창 A의 전용 참조처럼 사용하면 작업 의도와 실제 창이 달라집니다. 이것을 다른 앱 접근이나 공식 API 계약 위반으로 해석하지 않습니다.

2.2에서는 의도한 대상과 최신 공식 관측을 대조해 대상 불일치와 비교 불가를 구분해야 합니다. 도구의 `isError`만으로 이 문제를 감지할 수 없습니다. 이번 재선택은 실제 대상을 되돌린 검증 절차이며, CCUH의 자동 대상 검사나 자동 복구가 구현됐다는 뜻은 아닙니다. 서로 다른 창 제목을 이용한 재현으로, 같은 제목의 창 구분이나 고정 창 ID 확보를 검증한 결과는 아닙니다.

## 3. 내부처리

- [ ] **3.1 작업 실패 확인** — 입력이나 클릭의 오류와 실제 결과 미반영을 구분합니다. API가 반환됐다는 이유만으로 입력, 전송이나 저장이 끝났다고 하지 않습니다.
- [ ] **3.2 안전한 재시도** — 새 관측이나 유효한 참조로 조건이 달라졌을 때만 제한적으로 재시도합니다. 결과가 불확실한 전송이나 저장은 자동 반복하지 않습니다.
- [ ] **3.3 실제 실패 사례 검증** — 인식 또는 내부 작업이 실패했던 사례를 Computer Use 요청 하나로 재현하고, 보완 후 의도한 결과까지 확인합니다. 불필요한 정상 상황 반복 시험은 추가하지 않습니다.

## 공통 제약과 진행 방법

- Computer Use의 앱 접근 제한과 필요한 승인을 유지합니다. 공식 앱 핸들을 별도 AX 엔진의 권한으로 이전하지 않습니다.
- 사용자의 입력 대상을 임의로 전환하지 않습니다. 앱 인식 실패를 전경 앱 강제 활성화나 전역 키보드 입력으로 우회하지 않습니다.
- 대상이 모호하거나 접근이 거부되면 중단합니다. 막힌 지점과 필요한 다음 행동을 즉시 알리고, 같은 실패를 말없이 반복하지 않습니다.
- 각 항목은 개발, 검증, 리팩토링과 재검증을 마친 뒤 실제 결과로 완료 표시합니다. 합성 입력 검사나 과거 버전의 결과를 현재 기능의 완료로 옮기지 않습니다.
- 사용자 도움은 실제 실패 당시 상태 확인이나 본인의 승인처럼 자동화할 수 없는 경우에만 요청합니다.

## 기존 검증의 위치

호출 시작만 기록했던 수신기와 다른 도구 제외의 이전 근거는 Git 이력에 있습니다. 현재 반환 관측의 근거와 한계는 위 1.3 기록에 있으며, `~/.codex/ccuh/receiver/`의 메타데이터는 앱 작업의 성공 증거가 아닙니다.

계산기의 기존 허용과 체스 요청 취소는 공식 앱 접근 경계의 검증 기록입니다. 앱 인식 오류나 입력과 클릭 실패의 복구가 구현됐다는 의미로 사용하지 않습니다. 포커스 관측기와 그 CI 검사는 이번 개발 범위에서 제거했습니다.

새 결과는 해당 항목 아래에 검증한 소스와 설치본, 실제 실패, 조치와 결과, 남은 조건을 짧게 기록합니다. 이 파일을 유일한 진행표로 유지합니다.
