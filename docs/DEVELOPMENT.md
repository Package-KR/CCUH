# CCUH 개발 체크리스트

## 제품 목표

사용자가 Computer Use에 작업을 맡기면 CCUH가 자동으로 연결되어, 허용된 앱과 창에서 사용자의 작업을 방해하지 않고 실행되어야 합니다.

- Computer Use 외 경로에서는 CCUH 수신기와 UI 실행 경로가 호출되지 않아야 합니다.
- 사용자는 다른 앱, 데스크탑, 전체화면과 모니터에서 계속 작업할 수 있어야 합니다.
- 앱 접근 제한과 필요한 승인을 유지해야 합니다.
- 대상이 모호하거나 실행 결과가 불확실하면 중단하고 즉시 알려야 합니다.
- 카카오톡, 메모와 특정 대화 상대는 시험 예시입니다. 제품은 일반적인 외부 앱을 대상으로 합니다.

## 체크와 진행 규칙

체크는 적힌 버전과 조건에서 증거를 확인했다는 뜻입니다. 이전 설치본의 성공을 최신 소스의 완료로 옮기지 않습니다. 코드 구현, 격리 검사, 실제 설치본 검증을 구분합니다.

한 번에 아래 체크 한 항목을 진행합니다. 해당 단계의 완료 조건을 통과하지 못하면 뒤 기능을 만들지 않습니다. 조사 완료와 제품 조건 통과를 구분하며, 실패가 재현된 기능은 완료로 표시하지 않습니다.

## 현재 상태와 다음 작업

| 구분                      | 현재 상태                                                                |
| ------------------------- | ------------------------------------------------------------------------ |
| 최소 자동 수신            | 공유 CUA 호출의 수신 실험만 확인. 잘못된 적용 범위 때문에 자동 등록 중단 |
| 최신 설치본               | 로컬 0.0.0의 소스와 빈 훅 정의가 저장소와 일치                           |
| Computer Use 외 실행 차단 | 실패. 브라우저 전용 호출과 위조 입력의 수신을 재현                       |
| 앱 접근 제한과 포커스     | 미검증                                                                   |
| 창 탐색, 대상 유지와 동작 | 미구현                                                                   |
| CI와 릴리스               | 설정과 로컬 검사 완료. 원격 실행 결과는 별도 확인 필요                   |

**현재 중단 지점:** 2단계입니다. 현재 공식 훅 계약과 설치본에서 Computer Use 전용 출처를 검증할 수단을 찾지 못했습니다. `.codex-plugin/hooks.json`은 비워 두며 다른 기능은 추가하지 않습니다. 자동 수신도 함께 중단된 상태이므로, 이를 실행 차단 기능의 완성으로 해석하지 않습니다.

**재개 조건:** 브라우저 경로와 Computer Use를 구분하는 호스트 제공 실행 경계가 필요합니다. 그 경계에서 정상 요청의 자동 실행, 제외 요청의 프로세스 미생성, 위조 입력 방어를 각각 검증한 뒤에만 자동 훅을 다시 등록합니다. 이름, 코드 문자열, 부모 프로세스명, 환경변수나 자체 생성 토큰으로 이 조건을 대신하지 않습니다.

## 1. 자동 수신

**목적:** 모델이 CCUH 도구를 별도로 선택하지 않아도 실제 Computer Use 호출이 수신기를 실행하는지 확인합니다.

- [x] 공식 PreToolUse 명령 훅 하나와 최소 수신기로 자동 수신 실험을 했습니다.
- [x] 이전 설치본에서 실제 공유 CUA js 호출 B/C 후 새 수신 기록이 생긴 것을 확인했습니다.
- [x] 해당 실제 호출의 코드 해시와 수신기 소스 해시가 기록과 일치했습니다.
- [x] 리팩토링한 소스의 타입 검사와 23개 입력의 전후 동등성 검사를 통과했습니다.
- [x] 중단 조치를 반영한 로컬 설치본의 소스와 빈 훅 설정이 저장소와 일치합니다.
- [ ] 2단계 해결 후 최신 설치본에서 실제 Computer Use js 호출과 새 기록을 대조합니다.
- [ ] 2단계 해결 후 js_reset의 실제 자동 수신도 확인합니다.

**완료 조건:** 최신 설치본에서 두 지원 도구의 실제 Computer Use 호출과 수신을 연결할 수 있어야 합니다. 수신기를 직접 실행한 검사와 합성 이벤트는 이 증거로 사용하지 않습니다. B/C는 실제 명령 훅 실행의 증거이며, Computer Use 전용 출처나 앱 허용의 증거는 아닙니다. 현재 자동 등록 중단으로 이 단계도 완료 상태가 아닙니다.

## 2. Computer Use 외 실행 차단

**목적:** 다른 경로에서는 호출되지 않는다는 사용자 조건을 검증합니다. 현재 가장 먼저 해결할 기능 경계입니다.

- [x] 기존 정확한 도구명 매처와 수신기 필터로는 적용 범위를 구분하지 못함을 확인했습니다.
- [x] 훅의 플러그인 정보는 훅 소유자이며, 호출 도구의 출처 증명이 아님을 확인했습니다.
- [x] 현재 번들의 `cua_repl`이 `browser,computer` 경로를 공유함을 설정과 실제 호출로 확인했습니다.
- [x] 공식 계약과 설치된 App/CLI의 훅 스키마를 조사했습니다. 사용할 수 있는 호출 출처 증명은 찾지 못했습니다.
- [x] 브라우저 목록만 읽는 실제 호출에서 새 수신 기록이 생기는 실패를 재현했습니다.
- [x] 격리된 임시 경로에서 올바른 도구명을 넣은 위조 입력을 직접 실행하면 기록이 생기는 실패를 재현했습니다.
- [x] CCUH 자동 훅을 비우고 공식 `hooks/list`에서 CCUH 항목 0개를 확인했습니다. 이후 실제 CUA 호출에서도 수신 기록이 유지됐습니다.
- [ ] 일반 코딩, 셸, 검색과 다른 MCP 도구를 각각 호출하고 수신기 프로세스 생성이 0회인지 독립적으로 관측합니다.
- [ ] 위 검사에서 수신 기록도 변경되지 않는지 확인합니다. 기록 불변만으로 프로세스가 실행되지 않았다고 판단하지 않습니다.
- [ ] 정상 Computer Use 자동 실행과 함께 유지되는 호스트 실행 경계 및 직접 실행 방어를 확보합니다.
- [ ] 미신뢰, 비활성 훅과 작업 종료 이후에 별도의 실행 경로가 열리지 않는지 확인합니다.

**현재 미충족 조건:** 수신기는 공유 CUA 도구명을 검사할 뿐 호출자를 인증하지 않습니다. 같은 형식의 입력을 직접 전달하면 기록을 만들 수 있습니다. 실행 후 입력을 거절하는 것과 프로세스가 아예 시작되지 않는 것도 다릅니다. 자동 훅 중단은 잘못된 실행 경로를 닫는 조치이며, 전용 자동 실행 경계를 구현한 결과는 아닙니다.

**조사 근거:** [공식 훅 문서](https://learn.chatgpt.com/docs/hooks)는 도구명 매칭을 제공하지만 Computer Use만의 서명된 호출 출처를 제공하지 않습니다. 설치된 App `0.166.0-alpha.5.1`과 CLI `0.166.0`의 PreToolUse 스키마에도 해당 필드가 없습니다. [App Server의 requestAttestation](https://learn.chatgpt.com/docs/app-server)은 호스트의 upstream attestation이며 이 수신기의 특정 도구 호출 검증 수단이 아닙니다. 원격 MCP의 [클라이언트 인증](https://developers.openai.com/plugins/build/auth)도 로컬 명령 훅 출처와 구분합니다. 이 결론은 2026-11-02 확인한 계약과 설치본에 한정합니다.

**완료 조건:** 자동 호출 제외와 직접 실행 방어를 각각 증거로 판정해야 합니다. 사용자 요구인 절대 실행 금지를 단순 수신 거절로 충족했다고 표시하지 않습니다. 현재 호스트에서 필요한 보장을 제공할 수 없다면 해당 한계를 기록하고 이 단계에서 설계를 다시 선택합니다. 사용자 동의 없이 조건을 완화하거나 다음 기능으로 넘어가지 않습니다.

## 3. 앱 접근 제한

**목적:** Computer Use의 앱 접근 정책을 유지하면서 다음 실행 단계로 연결합니다.

- [ ] 같은 작업의 앱 허용, 승인 대기와 거부를 구별할 수 있는 공식 증거를 확인합니다.
- [ ] 앱 목록, 창 제목과 임의 JS 호출의 성공을 앱 접근 허용으로 해석하지 않습니다.
- [ ] 허용된 앱만 후속 조회로 넘기고 다른 앱으로 대상이 바뀌면 허용 상태를 재확인합니다.
- [ ] 거부된 앱과 승인 대기 중인 앱에 대한 앱 및 네이티브 접근이 0회인지 확인합니다.
- [ ] 권한 오류와 미확인 상태에서 다른 도구, 이름이나 전경 입력으로 우회하지 않는지 확인합니다.

**판정 구분:** PreToolUse 수신은 앱 승인보다 먼저 일어날 수 있습니다. 앱 거부 시험에서는 수신 로그가 아니라 앱 및 네이티브 접근 여부를 확인합니다.

**완료 조건:** 허용과 거부가 같은 실제 연결 경로에서 유지되어야 합니다. 공식 허용 정보를 이어받을 방법이 확인되기 전에는 별도 앱 조회 엔진을 만들지 않습니다.

## 4. 사용자 포커스 분리

**목적:** 사용자의 화면과 입력 대상을 유지하면서 AI의 작업을 수행할 수 있는지 확인합니다.

- [ ] 첫 호출 전부터 종료 후까지 화면, 전경 앱과 키보드 입력 대상을 구분해 관측합니다.
- [ ] 시험 앱의 시작과 종료도 포함하며 잠깐의 활성화도 누락하지 않습니다.
- [ ] 사용자가 직접 전환한 이벤트와 AI 또는 시험 앱이 만든 간섭을 구분합니다. 출처가 불명확하면 미확인으로 둡니다.
- [ ] 사용자가 같은 데스크탑의 다른 앱을 쓰는 조건을 확인합니다.
- [ ] 다른 데스크탑, macOS 전체화면, 최소화와 복원, 여러 모니터 조건을 자동화 가능한 범위에서 확인합니다.
- [ ] 실제 동시 입력 확인이 필요한 부분만 사용자에게 요청하고 입력 문자 원문은 기록하지 않습니다.
- [ ] 오류와 시간 초과에서도 원래 도구가 포커스를 바꾸는 경로로 실행되지 않는지 확인합니다.

**완료 조건:** 시작, 실행, 실패와 정리 전 과정에서 AI가 사용자 작업을 방해하지 않아야 합니다. 시작과 끝의 전경 앱이 같다는 사실만으로 중간 간섭이 없었다고 판정하지 않습니다.

## 5. 대상 발견과 유지

**목적:** 사용자 전경과 무관하게 지정한 앱과 창을 정확히 식별하고 같은 대상을 유지합니다.

- [ ] 앱 식별자와 정확한 창 식별을 읽기 전용으로 확보합니다.
- [ ] 사용자가 선택한 전경 창을 AI의 작업 대상으로 자동 채택하지 않습니다.
- [ ] 같은 제목의 여러 창, 부분 목록과 다른 데스크탑의 창을 구별하고 모호하면 중단합니다.
- [ ] 사용자 앱 전환 이후에도 기존 대상 참조가 유지되는지 확인합니다.
- [ ] 창 닫기, 앱 종료와 식별자 재사용에서 기존 참조를 무효화하고 새 창에 자동 재연결하지 않습니다.
- [ ] 대상 변경, 예상과 다른 관측과 작업 재개 때만 필요한 재조회를 수행합니다. 조건 변화 없는 같은 실패를 반복하지 않습니다.
- [ ] 브라우저 탭 핸들, 앱 창 참조와 서로 다른 도구의 요소 식별자를 혼용하지 않습니다.

**완료 조건:** 실제 창과 식별 결과를 대조할 수 있고, 참조가 유효하거나 중단해야 하는 이유가 명확해야 합니다. 탐색 중에도 2~4단계의 조건을 유지해야 합니다.

## 6. 백그라운드 동작

**목적:** 정확한 대상에서 허용된 동작 하나를 수행하고 실제 결과를 확인합니다.

- [ ] 자체 시험 앱의 입력란 하나에 값을 변경하고 실제 값과 실행 횟수를 확인합니다.
- [ ] 버튼 하나를 실행하고 별도 상태 변화로 성공 여부를 확인합니다.
- [ ] 보안 입력란, 비활성 요소, 오래된 참조와 다른 창의 요소를 거절합니다.
- [ ] 동작 직전 대상, 예상 값과 허용 범위를 재확인합니다.
- [ ] 불확실한 결과에서 자동 재전송이나 중복 실행을 하지 않습니다.
- [ ] 시험 앱 검증 뒤 필요한 외부 앱 사례만 확인합니다. 값 변경을 메시지 전달이나 저장 완료로 보고하지 않습니다.

**완료 조건:** 대상, 단일 실행, 실제 결과와 사용자 작업 비간섭을 모두 확인해야 합니다. 지원하지 않는 동작을 전경 키보드나 마우스 조작으로 바꾸지 않습니다.

## 7. 실패와 수명 관리

**목적:** 실패를 숨기지 않고 작업과 자원을 정리합니다.

- [ ] 취소, 시간 초과, 연결 끊김과 앱 종료에서 실행을 중단합니다.
- [ ] 앱 접근 권한이 철회되면 후속 접근을 막습니다.
- [ ] 작업 종료 후 소유한 세션, 관측기와 하위 프로세스가 남지 않는지 확인합니다.
- [ ] 재시작 후 오래된 창과 요소 참조를 재사용하지 않습니다.
- [ ] 같은 실패의 반복 횟수와 시간 한도를 정하고 초과 시 중단합니다.
- [ ] 막힌 지점, 확인된 사실과 필요한 사용자 행동만 즉시 알립니다.

**완료 조건:** 실패를 성공으로 처리하거나 조용히 반복하지 않아야 합니다. 정리 과정도 사용자 작업을 방해하지 않아야 합니다.

## 8. 설치본 통합 검증

**목적:** 사용자의 Computer Use 요청 하나로 전체 흐름을 재현합니다.

- [ ] 최신 커밋과 설치본의 코드 및 설정이 일치하는지 확인합니다.
