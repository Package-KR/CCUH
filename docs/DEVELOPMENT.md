# CCUH 개발 계획

## 목표와 범위

사용자가 Computer Use만 요청해도 CCUH가 자동으로 연결되고, 허용된 대상에서 사용자 작업을 방해하지 않고 실행되어야 합니다.

- 작동 범위는 사용자가 허용한 Computer Use 작업입니다. 일반 코딩, 셸, 검색과 다른 도구에는 작동하지 않습니다.
- 앱 접근 제한과 필요한 승인을 그대로 따릅니다. 창 목록에 나타난 사실이나 도구 이름을 접근 허용의 증거로 사용하지 않습니다.
- 사용자 포커스와 AI의 작업 대상을 구분합니다. 첫 호출과 시험 앱의 시작 및 종료도 검증 범위에 포함합니다.
- 카카오톡과 메모는 시험 예시입니다. 특정 앱이나 대화 상대에 맞춘 제품으로 설계하지 않습니다.
- 모호한 대상, 권한 거부, 참조 만료와 불확실한 동작 결과에서는 중단합니다. 전경 입력으로 전환하거나 전송을 반복하지 않습니다.

## 진행 현황

| 1    | 미착수 | 자동 연결 가능성                | 실제 Computer Use 이벤트가 CCUH를 직접 호출하고, 앱 제한과 최초 포커스 유지가 함께 확인됨 |
| 2    | 미착수 | 대상 발견                       | 허용된 앱과 정확한 창을 읽기 전용으로 식별하며 모호하면 중단함                            |

기존 구현의 검사 결과를 새 단계의 완료 증거로 옮기지 않습니다. 현재 완료한 것은 초기화뿐입니다.

## 1. 자동 연결 가능성

이 단계에서는 창 탐색기나 입력 엔진을 만들지 않습니다. 고정된 무동작 응답을 반환하는 최소 수신기와 자동 호출 경로만 준비합니다.

1. 현재 Codex의 공식 연결 방법과 훅 출력 계약을 확인합니다. MCP 도구 훅은 조사 후보이며 채택이 확정된 설계는 아닙니다.
2. 실제 Computer Use 호출과 자동 수신을 같은 호출 식별자로 연결합니다. 별도 CCUH 도구 선택이나 합성 이벤트 전달을 실제 자동 실행으로 계산하지 않습니다.
3. 공식 앱 접근 허용과 거부를 구별할 수 있는 증거를 확인합니다. 성공한 임의 JS 호출을 앱 승인으로 해석하지 않습니다. 무동작 응답만으로 접근 제한 유지가 검증됐다고 하지 않습니다.
4. 허용된 요청 뒤의 읽기 전용 시험 작업에서 CCUH 자동 진입을 확인합니다. 거부된 요청에서는 네이티브 접근이 없어야 합니다.
5. 시험 앱 시작 전부터 종료 후까지 전경 앱과 실제 입력 대상의 변화를 별도로 관측합니다. 앱 시작 시의 잠깐의 활성화도 실패로 기록합니다.
6. 오류, 시간 초과와 연결 끊김에서 기존 호출이 계속되는지 확인합니다. 훅의 실패 처리만으로 포커스 보존을 보장한다고 추정하지 않습니다.
7. 일반 코딩과 다른 도구 호출에서는 CCUH의 UI 접근이 없어야 합니다.

**진행 조건:** 자동 호출, 앱 제한, 첫 호출부터의 포커스 유지가 같은 실제 경로에서 모두 확인되어야 합니다. 하나라도 확인할 수 없으면 원인과 필요한 호스트 기능을 정리하고 연결 설계를 다시 선택합니다. 뒤 단계의 기능으로 이 문제를 덮지 않습니다.

## 2. 대상 발견

허용된 앱의 창 제목, 앱 식별자와 창 식별자를 읽기만 합니다. 전경 앱은 작업 대상의 기본값으로 사용하지 않습니다.

유일한 대상, 같은 제목의 여러 창, 다른 데스크탑과 전체화면 뒤의 창을 구별합니다. 부분 목록은 전체 목록처럼 취급하지 않고, 모호하거나 권한이 없으면 중단합니다.

**진행 조건:** 식별 결과와 실제 창을 대조한 증거가 있으며, 발견 과정에서 앱 활성화나 입력이 없어야 합니다.

## 3. 대상 유지

확보한 창 참조를 작업에 묶고, 사용자 포커스 변경으로 다시 선택하지 않습니다.

재조회는 사용자가 요청한 작업을 이어갈 때, 대상 상태가 바뀌었을 때, 관측 결과가 예상과 다를 때 수행합니다. 같은 실패를 조건 변화 없이 반복하거나 상시 폴링하지 않습니다. 창 닫기, 앱 종료와 식별자 재사용 시 기존 참조를 무효화합니다.

**진행 조건:** 사용자 앱 전환, 데스크탑 전환, 전체화면, 최소화와 복원에서 참조 처리 결과가 명확해야 합니다. 닫았다가 다시 연 창은 명시적으로 새 대상을 확보해야 합니다.

## 4. 동작 실행

자체 시험 앱에서 값 변경 한 번과 버튼 실행 한 번부터 확인합니다. 입력할 값, 대상 요소, 실행 전 상태와 기대 결과를 명시합니다.

실제 변경 결과와 실행 횟수를 독립적으로 확인합니다. 보안 입력란, 비활성 요소, 오래된 참조와 다른 창의 요소는 차단합니다. 불확실한 전송이나 저장은 자동 재시도하지 않습니다.

**진행 조건:** 올바른 대상의 결과와 단일 실행이 확인되고 사용자 작업에 영향이 없어야 합니다. 요소 변화만 확인한 경우 메시지 전달이나 저장 완료까지 확인했다고 하지 않습니다.

## 5. 실패와 수명 관리

취소, 시간 초과, 연결 끊김, 앱 종료, 접근 권한 철회와 재시작을 검증합니다. 작업이 끝나면 소유한 세션, 관측기와 하위 프로세스를 정리합니다.

**진행 조건:** 실패한 작업을 성공으로 보고하지 않으며, 권한이 사라진 뒤의 접근과 자동 중복 실행이 없어야 합니다. 정리 동작도 사용자의 화면과 포커스를 바꾸지 않아야 합니다.

## 6. 통합과 배포

Computer Use만 요청한 새 작업에서 허용, 거부, 잘못된 대상과 동작 실패를 검증합니다. 사용자나 모델이 CCUH 도구를 별도로 고르는 과정을 자동 연결로 보고하지 않습니다.

배포 패키지는 검증한 실행 경로를 사용해야 합니다. Codex App과 CLI는 각각 검증하고, 설치와 훅 신뢰 승인을 구분합니다. 이 단계에서 패키지 명령, CI와 릴리스를 다시 연결합니다.

**진행 조건:** 실제 설치본의 코드 식별과 전 과정 결과가 개발본의 검증 근거와 일치해야 합니다.

한 번에 한 단계의 한 가지 가설을 다룹니다. 단계마다 아래 항목을 이 문서에 기록하며, 독립적인 진행표를 늘리지 않습니다.

| 항목      | 기록할 내용                           |
| --------- | ------------------------------------- |
| 가설      | 이번에 무엇을 확인하려는지            |
| 범위      | 변경할 계층과 허용된 작업             |

| 결과      | 통과, 실패, 미확인과 실제 근거        |
| 다음 행동 | 현재 단계를 계속할지 다음 단계로 갈지 |

재현과 검증은 가능한 범위에서 자동화합니다. 사람의 동시 작업처럼 자동 관측으로 확인할 수 없는 항목만 사용자에게 요청하며, 필요한 이유와 한 가지 행동을 명확히 설명합니다. 검사 개수만으로 기능 완료를 판단하지 않습니다.

## 폴더 사용 원칙

기존 아키텍처 폴더는 유지합니다. 각 단계에서 책임이 생길 때 필요한 최소 파일만 추가합니다. 아직 선택하지 않은 연결 방식이나 엔진을 위한 추상화, 설치기와 배포 코드를 미리 만들지 않습니다.

현재 저장소에는 실행 구현이 없습니다. 저장소 밖에 이미 설치된 CCUH나 Codex 캐시의 제거 또는 비활성화는 이 초기화에 포함하지 않았습니다.
