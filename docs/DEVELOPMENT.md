# CCUH 개발 체크리스트

## 목적과 범위

Computer Use가 작업할 앱을 인식하는 부분과, 인식한 앱 안에서 입력이나 클릭 등의 작업이 실패하는 부분을 보완합니다.

기존 자동 수신은 연결 기반으로 유지합니다. 실제 보완 기능은 앱 인식 문제와 앱 내부 작업 실패에 집중하며, 일반적인 전체화면이나 모니터 배치 시험을 별도 개발 단계로 늘리지 않습니다.

## 도메인 구조

| 도메인   | 폴더               | 책임                                                            |
| -------- | ------------------ | --------------------------------------------------------------- |
| 공통     | `src/common/`      | Computer Use 연결, 호출과 결과 연결, 공통 오류 형식과 최소 로그 |
| 인식     | `src/recognition/` | 의도한 앱과 창 식별, 잘못된 대상과 오래된 참조 처리             |
| 내부처리 | `src/interaction/` | 앱 내부 입력과 클릭 등의 실패 확인, 결과 검증과 안전한 재시도   |

현재 구현은 `src/common/hooks/receiver.ts`의 호출 전후 수신기와 지침 전달, `src/recognition/classify.ts`의 분류 함수, `src/recognition/guard.ts`의 대상 가드와 작업 검증, `src/interaction/outcome.ts`의 결과 분류입니다. 동반 스킬과 생성된 REPL 도우미를 통해 공식 Computer Use 작업에 연결합니다.

## 현재 위치

**3.3에서 실제 창 불일치의 재선택과 클릭 무반영 감지 후 별도 취소 복구를 확인했습니다.** 검증 중 발견한 필드 ID 오인식을 수정하고 실제 기본 입력을 재확인했습니다. 실제 둘째 setter를 통한 자동 복구는 아직 관측하지 못해 3.3을 완료로 표시하지 않습니다. 관측된 UI 변화와 저장 파일 또는 서버 처리 완료를 구분하며, 임의 CUA 코드를 호스트에서 강제로 재작성하지 않습니다.

### 관측 한계

- `last-start.json`, `last-receipt.json`, `last-result.json`은 각각 최신 기록입니다. 서로 인접한 파일이라고 같은 호출은 아니며 세션과 호출 해시가 일치해야 합니다. 동시 호출 전체 이력은 보존하지 않습니다.
- `isError: false`는 도구 반환에 실린 값입니다. 올바른 앱 인식, 입력, 클릭, 저장이나 전송의 성공 증거가 아닙니다. 오류 플래그가 없거나 boolean이 아니면 `null`로 기록합니다.
- 이번 설치 환경의 오류 던지기 시험에서는 해당 호출의 호출 후 훅 수신이 관측되지 않았습니다. 반환 기록 부재만으로 오류, 취소, 시간 초과나 서버 종료 중 어느 원인인지 단정하지 않습니다. 확인한 설치 버전의 공식 훅 이벤트 목록에는 별도 도구 실패 이벤트가 없습니다.
- 호출 전 입력은 256 KiB, 호출 후 입력은 8 MiB까지 읽어 해석합니다. 호출 후 상한을 넘으면 `input_limit_exceeded`만 기록하고 호출 및 응답 정보는 미확인으로 둡니다. 원래 응답은 바꾸지 않으며 오류 본문이나 화면 내용은 저장하지 않습니다.
- 최신 상태 파일은 원자적으로 교체합니다. 쓰기 도중 프로세스가 강제 종료되면 `.pending` 파일이 남을 수 있습니다.
- 이름이 일치하는 공유 CUA 호출만 수신하지만, 도구 이름은 사용자 플러그인 선택의 인증이나 앱 접근 승인이 아닙니다. 앱 승인과 실제 UI 결과는 이후 단계에서 별도로 확인합니다.

### 확인한 원인과 다음 구현 경계

### 2.2 분류 계약

`classifyRecognition(request, observation, policy)`는 호출자가 제공한 정규화된 일반 데이터 객체를 분류합니다. 앱을 조회하거나 조작하지 않고, 권한을 허용하거나 재시도하지 않으며, 입력 원문을 저장하지 않습니다. 요청과 관측에 실린 값이나 요청 ID가 증거의 출처를 인증하지는 않습니다.

| 분류      | 확인하는 내용                                                                                       |
| --------- | --------------------------------------------------------------------------------------------------- |
| `failed`  | 명시적으로 제공된 접근 거부, 앱 또는 창 없음, 참조 무효화, 비교 가능한 앱 또는 창 선택 조건 불일치  |
| `matched` | 요청한 선택 조건과 관측 값의 일치. 앱 범위와 창 범위를 구분하고 비교 근거를 `basis`에 남김          |
| `unknown` | 다른 요청, 오래됐거나 미래 시각인 관측, 불충분하거나 모호한 대상, 비교할 수 없는 식별자와 형식 오류 |

명시적 실패 종류는 CCUH 내부의 정규화 계약입니다. 공식 도구가 이 이름의 오류 코드를 반환한다는 뜻이 아니며, 일반 예외의 문구만 보고 접근 거부나 대상 없음을 추정하지 않습니다. 연결부는 실제 근거가 확인된 경우에만 해당 종류를 제공해야 합니다.

같은 요청인지와 관측 시각을 먼저 확인합니다. `nowMs`와 `maxAgeMs`는 호출자가 명시하며 기본 허용 시간을 만들지 않았습니다. 모호한 관측으로 특정 대상을 확정하지 않고, 비교 가능한 앱 조건이 다르면 창 비교를 진행하지 않습니다. 창 ID는 앱 식별자가 bundle ID이고 식별자 namespace도 같을 때만 비교합니다. 앱 표시명과 창 제목은 NFC로 정규화해 비교하되, ID와 제목을 서로 대신하지 않습니다.

`basis: ['app-name', 'window-title']`의 일치는 표시명과 제목 조건이 같다는 뜻입니다. 동일한 안정 창 ID, 앱 접근 승인이나 후속 입력의 성공을 보장하지 않습니다. 관측 후 대상이 바뀌는 문제와 실제 작업 전 재확인은 2.3에서 다룹니다.

- 검증 중 한 차례 창 메뉴 대신 편집 메뉴가 관측되어 선택을 중단했습니다. 원인을 확정하거나 권한 오류로 바꾸지 않았으며, 메뉴 취소 후 최신 상태를 읽고 한 앱 객체로 선택을 이어갔습니다. 이 메뉴 오류의 자동 감지나 복구를 완료로 표시하지 않습니다.

  2.2 당시에는 개발 소스의 분류 함수까지만 검증했으며 공통 훅이나 설치된 플러그인에 자동 연결하지 않았습니다. 실제 접근 거부와 참조 무효화를 이 검사에서 새로 발생시켰다는 의미도 아닙니다. 이후 연결부 구현과 검증은 아래 2.3 기록에서 구분합니다.

### 2.3 연결 계약

지원하는 CUA 호출의 PreToolUse와 PostToolUse에서 고정된 `additionalContext`를 제공합니다. 등록된 `ccuh:ccuh` 스킬은 공식 App 객체와 의도한 앱 표시명 및 창 제목으로 대상 바인딩을 만듭니다. 훅이 UI 원문을 해석해 대상을 추정하거나 접근 허용을 결정하지는 않습니다.

`createTarget()`은 의도한 조건을 REPL 메모리에 유지합니다. `withTarget()`은 같은 App 객체의 전체 최신 상태를 읽고 2.2 분류기를 적용한 뒤, 조건이 맞을 때만 작업 콜백을 한 번 실행합니다. 전달된 최신 상태에서 인덱스를 찾아야 하며, 다른 객체나 이전 상태에서 얻은 인덱스를 재사용하지 않습니다.

창 조건만 다르고 공식 재선택 경로가 주어졌다면 그 경로를 한 번 호출하고 다시 관측합니다. `selectWindowFromMenu()`는 같은 앱의 실제 메뉴 모음과 popup 라벨, 유일한 제목 및 표준 창 항목을 확인합니다. 클릭이 반환됐다는 것만으로 성공하지 않으며, 가드의 새 관측이 일치해야 콜백을 실행합니다. 앱 불일치, 잘못된 헤더, 접근 예외와 불확실한 대상은 중단합니다.

`prepareTarget()`의 결과는 그 시점의 검사 요약입니다. 이후 `withTarget()`은 다시 검사합니다. `executed`는 콜백이 반환됐다는 뜻이며 저장이나 전송의 성공 판정이 아닙니다. 콜백이 정상 반환되면 대상을 다시 읽습니다. 대상이 바뀌거나 콜백에서 예외가 발생해도 이미 시도한 작업을 반복하지 않습니다. 같은 App 객체의 가드 작업이 겹치면 후속 호출을 중단합니다.

### 2.3의 한계

이 연결은 모델이 지침을 따라 가드를 사용하는 에이전트 워크플로입니다. Pre 지침은 이미 작성된 현재 호출을 바꾸지 않으며, 임의 CUA JavaScript를 호스트에서 강제로 가드에 통과시키는 기능이 아닙니다. 스킬의 암묵적 선택도 실행 강제가 아닙니다. 새 관측과 작업 사이에 사용자가 상태를 바꿀 가능성을 없애지는 못합니다.

현재 가드는 표시명과 제목 조건을 비교합니다. 같은 제목의 여러 창을 안정 ID로 구분하는 기능이나 모든 앱의 재선택 경로를 제공하지 않습니다. 유일한 실제 메뉴 항목이 확인되는 공식 경로만 검증하며, 다른 앱 객체, 비공개 AX 엔진, 앱 강제 활성화나 전역 키 입력으로 실패를 우회하지 않습니다. 거부된 App 접근을 다시 허용하는 캐시나 별도 MCP는 추가하지 않았습니다.

### 3.1 작업 결과 검증 계약과 현재 근거

`withVerifiedTarget(target, action, verify)`는 같은 공식 App의 대상 확인 뒤 작업을 한 번 실행하고, 예외가 나도 최신 상태를 다시 읽습니다. 호출 결과 `invocation: returned/threw`와 관측 결과 `confirmed/not-observed/unknown`을 별도로 반환합니다. 기존 `withTarget`의 동작은 유지합니다.

검증기는 같은 대상의 변경된 전체 AX 스냅샷 `before/after`만 받아 요청한 변화가 확인되면 true, 관측되지 않으면 false, 판단이 어려우면 unknown을 반환합니다. 동일한 스냅샷은 검증기를 호출하지 않고 `no-observable-change`로 남깁니다. 작업 후 대상이 달라졌거나 관측할 수 없으면 재선택하지 않고 unknown으로 중단합니다. 검증기 오류도 unknown입니다. 자동 재시도와 반복 조회는 없으며 원문과 예외 본문을 로그에 저장하지 않습니다.

`checked`는 확인 절차를 수행했다는 뜻이며 성공 판정이 아닙니다. `not-observed`도 해당 관측에서 변화가 확인되지 않았다는 뜻으로, 영구 실패나 재시도 허용을 의미하지 않습니다. 전송 검증은 이전부터 있던 같은 메시지나 입력란 비움과 구분되는 새 근거가 필요합니다. 창을 닫거나 다른 대상으로 이동하는 작업은 이 같은 대상 검증 경로에서 확정할 수 없습니다.

격리된 앱 대역으로 21개 시나리오를 개발 소스와 생성 JavaScript에서 각각 실행했습니다. 변화 반영, 반환됐지만 변화 없음, 관련 없는 변화, 반영 후 예외, 반영 전 예외, 대상 변경과 조회 실패, 검증기 오류, 동시/중첩 호출 차단, 제목 없는 시트의 앱 범위 처리, 기존 API 동작과 작업/재선택 횟수 제한이 통과했습니다. 빌더는 새 내부 모듈을 포함하며 허용하지 않은 의존성 11종을 거부했습니다. 이 검사는 실제 앱이나 Computer Use를 호출하지 않았으며 실제 연동 근거로 확대하지 않습니다. 영구 테스트 파일이나 추가 패키지는 만들지 않았습니다.

### 3.1 실제 Computer Use 검증과 발견한 한계

공식 TextEdit App 객체를 얻고 설치된 도우미를 CUA REPL에 로드해, 새로 만든 시험 문서에서 다음을 확인했습니다. 별도 UI 엔진이나 MCP 작업 도구를 선택하지 않았으며 실제 Pre/Post 지침이 호출에 전달됐습니다.

| 실제 시험                                     | 호출과 관측 결과                                                                          |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 본문 A에서 B로 변경                           | 입력1회, returned와 confirmed                                                             |
| 볼드체 체크상자0에서1로 변경                  | 클릭1회, returned와 confirmed                                                             |
| 이미 선택된 정렬 체크상자 클릭                | 클릭1회, returned지만 not-observed. 자동 반복 없음                                        |
| 본문 B에서 C로 변경한 뒤 의도적으로 예외 발생 | 입력1회, threw와 AX 기준 confirmed. 실제 CUA API의 자연 발생 예외가 아닌 제어된 오류 주입 |
| 제목 없는 GoToWindow 시트의 경로 변경         | 앱 범위에서 입력1회, returned와 confirmed                                                 |

최초 문서 입력에서 AX 값의 표기와 포커스 요약 행을 검증기가 제대로 구분하지 못했을 때는 unknown을 반환했습니다. 실제 입력란 한 행만 비교하도록 시험 검증기를 바로잡았습니다. 문서 제목이 `.rtf`를 포함하도록 바뀌었을 때도 입력 전에 차단했으며 그 시도의 입력 횟수는0이었습니다. 관측한 새 제목을 기준으로 의도한 시험 문서를 다시 선택했습니다.

제목이 빈 macOS 시트에서는 기존 헤더 해석이 앱 범위 요청까지 거부하는 결함을 발견해 수정했습니다. 정확히 빈 제목은 창 관측을 생략하고 유효한 앱 이름을 비교합니다. 특정 창을 요구하는 요청은 계속 window-unobserved로 차단합니다. 실제 시트의 고유 ID와 필드를 콜백에서 확인한 뒤 경로 입력을 수행했습니다.

저장까지 관찰한 결과, 제어된 예외 직후 AX에는 C가 있었지만 최종 RTF를 텍스트로 변환하면 B가 남았습니다. 따라서 AX의 순간적인 값 일치가 문서 모델 반영이나 저장 완료를 보장하지 않는다는 한계가 실제로 확인됐습니다. 저장 성공을 보고할 때는 저장 파일 등 별도의 완료 근거가 필요하며, threw를 받은 호출은 AX 변화가 보여도 자동 반복하면 안 됩니다. 이번 결과를 모든 앱의 입력, 저장 또는 전송 완료 검증으로 확대하지 않습니다.

시험 문서는 임시 폴더에 저장하고 시험 창이 닫혀 원래 문서로 돌아온 상태까지 확인했습니다. 최종 도우미 소스 해시는 `6156bdbca8837c74237a450355ccb552bf7ada5b537dc9c9e7e4886dab7d2874`입니다. 소스와 설치본이 일치하고 사용자가 두 훅을 재검토했습니다. 마지막 실제 호출의 전후 세션, 호출과 코드 해시가 일치했으며 호출 해시는 `8d9eeecc1f0c8fe8cd979e6e10791406eac6e304249edfae7585f00c3928acfe`입니다. 이 마지막 호출은 최종 도우미의 시트 입력과 시험 문서 정리 경로이며, 앞선 본문과 클릭 시험의 호출로 혼동하지 않습니다.

### 3.2 로컬 초안 교체 계약과 현재 근거

`setDraftValue(target, { effect: 'local-draft', fieldId, value, readValue })`는 같은 공식 App의 setValue만 사용합니다. 전송, 저장, 제출, 붙여넣기, 덧붙이기와 토글을 재시도하는 API는 없습니다. 명시한 필드는 외부 동작을 일으키지 않는 로컬 초안이어야 하며, 그 의미를 확인할 수 없으면 사용하지 않습니다. 선언 자체가 안전성이나 접근 승인의 증거는 아닙니다.

최신 전체 AX 스냅샷에서 고유한 ID와 편집 가능 속성, 중복되지 않은 인덱스를 가진 필드를 확인합니다. readValue는 제공된 같은 행과 스냅샷에서 문자열 값만 동기적으로 읽으며 앱을 조회하거나 조작하지 않습니다. 여러 ID 표기, 값 속 편집 가능 문구와 중복 인덱스는 모호한 증거로 중단합니다. 표시된 ID와 인덱스는 선택 조건이며 물리적인 객체 정체나 인증을 보장하지 않습니다.

한 호출의 setter는 최대 두 번입니다. 원하는 값이 이미 보이면 쓰지 않습니다. 첫 호출이 정상 반환됐고, 같은 필드의 값이 원래 값 그대로이며, 인덱스가 바뀐 경우에만 재시도 후보가 됩니다. 두 번째 쓰기 직전에 다시 관측해 같은 조건을 확인하며, 첫 효과가 늦게 나타나면 쓰지 않고 사용자 편집으로 보이는 다른 값은 덮어쓰지 않습니다. setter 예외, 대상/필드 미확인과 같은 참조는 반복하지 않습니다. 사용자 입력과 체크 사이를 원자적으로 잠글 수 없으므로 마지막 확인 뒤의 동시 편집 가능성은 남습니다.

정책은 interaction/retry.ts, 실행 흐름은 interaction/draft.ts가 담당합니다. recognition/guard.ts는 기존 대상 가드와 앱 잠금 안에서 이를 연결합니다. 앱 대역 36개 상황을 소스와 생성 JavaScript에서 각각 검사해 새 참조 재시도, 두 번째 실패의 상한, 늦은 반영, 사용자 값 변경, 예외 후 중단, 잘못된 필드 선택 방지, 중첩과 동시 호출 차단 및 값 원문 비노출을 확인했습니다. 순수 정책의 입력 조합 36개, 기존 3.1의 21개 상황과 빌더의 잘못된 의존성 24종도 확인했습니다. 이 결과는 실제 앱에서 재시도가 발생했다는 증거가 아닙니다. 실제 실패의 전체 복구는 3.3에서 별도로 확인합니다.

### 3.3 필드 선택 결함과 수정 범위

임시 앱 대역에서 `text field (settable), Value: ID: PathTextField`에 실제 ID 메타데이터가 없는데도 setter가 1회 실행되는 결함을 재현했습니다. 기존 검사가 값 안의 공백 뒤 `ID:`도 식별자로 받아들인 것이 원인이었습니다. 고유 ID 문구를 세는 기존 모호성 검사는 유지하고, 선택에 사용하는 문구는 렌더링 본문 시작 또는 쉼표 뒤에 있는 경우로 제한했습니다. 지원하지 않는 구분자와 중복 ID, 읽기 전용 값과 중복 숫자 참조는 쓰기 전에 차단합니다.

새 경계 사례 12개를 TypeScript와 생성 JavaScript에서 각각 실행해 통과했습니다. 기존 setter 시나리오 36개와 작업 검증 21개도 두 실행 형태에서 통과했으며, 빌더의 잘못된 의존성 24종, 타입과 문법 검사를 다시 확인했습니다. 임시 검사는 저장소 밖에서 수행했고 영구 테스트나 패키지를 추가하지 않았습니다.

문자열로 렌더링된 AX에서는 실제 값의 `, ID:`와 메타데이터가 구분되지 않을 수 있습니다. 이 수정은 확인된 공백 구분 오인식을 차단하며 모든 값 위조를 해결하거나 필드의 물리적 정체를 증명하지 않습니다. 값과 메타데이터를 확실히 읽을 수 없으면 `readValue`가 undefined를 반환해야 하며 자동 초안 교체를 사용하지 않습니다.

실제 앱에서 첫 setter가 반환되고 원래 값이 유지되면서 참조가 바뀌는 조건은 이번에 발생하지 않았습니다. 모든 실제 setter는 첫 입력으로 반영됐습니다. 첫 호출을 일부러 무시하거나 관측을 조작해 성공 사례를 만들지 않았으며, 실제 둘째 setter의 자동 복구는 3.3.3의 미완료 조건으로 남깁니다.

## 기존 검증의 위치

호출 시작만 기록했던 수신기와 다른 도구 제외의 이전 근거는 Git 이력에 있습니다. 현재 반환 관측의 근거와 한계는 위 1.3 기록에 있으며, `~/.codex/ccuh/receiver/`의 메타데이터는 앱 작업의 성공 증거가 아닙니다.

새 결과는 해당 항목 아래에 검증한 소스와 설치본, 실제 실패, 조치와 결과, 남은 조건을 짧게 기록합니다. 이 파일을 유일한 진행표로 유지합니다.

## 릴리스 버전 판정

`main`의 검증된 커밋을 기준으로 현재 메타데이터 버전의 정확한 태그부터 새 커밋 전체를 분석합니다. 과거 리셋 전의 높은 버전 태그나 마지막 병합 제목만으로 증가 폭을 결정하지 않습니다. 기준 태그가 없거나 현재 커밋의 조상이 아니면 자동 판정을 중단합니다.

- `feat:`는 minor, `!` 표기와 `BREAKING CHANGE:` 또는 `BREAKING-CHANGE:` footer는 major로 판정합니다. 일반 병합 제목에도 명시적인 breaking footer가 있으면 major입니다.
- `fix:`와 나머지 변경은 기존 정책대로 patch를 발행합니다. 여러 종류가 섞이면 major, minor, patch 순으로 가장 큰 증가 폭을 한 번 적용합니다.
- 기본 입력은 `auto`이며 수동 실행의 patch, minor와 major 선택은 명시적인 재정의로 유지합니다. 최초 `0.0.0` 발행과 기존 릴리스 재실행 및 `repair_tag` 경로도 유지합니다.
- 일반 병합에서는 내부 기능 커밋까지 읽습니다. squash로 합칠 때는 기능을 나타내는 PR 제목의 `feat:`를 유지해야 합니다. 본문의 단순 `feat:` 예문으로 기능 추가를 추정하지 않습니다.

판정 표기는 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)을 참고하며, 다른 종류의 patch 발행은 CCUH의 기존 정책입니다. 예를 들어 기준 버전이 `0.0.6`이고 그 뒤에 `feat`가 있으면 다음 버전은 `0.1.0`입니다. 이미 발행한 태그를 이동하거나 덮어쓰지는 않습니다.

임시 Git 저장소 9개에서 커밋 판정, 일반 병합 내부의 기능, 우선순위, 버전 파일 동기화, 기준 태그 오류, 최초 발행과 재실행 및 재공개 분기 등 45건을 확인했습니다. 실제 워크플로 실행 블록의 셸 문법도 검사했습니다. 원격 푸시나 GitHub Release 발행은 실행하지 않았으며 이 변경은 `main` 반영 이후 적용됩니다.

추가로 검사 시점의 로컬 `origin/main` 스냅샷을 별도 저장소에 복제하고 이번 변경을 `feat`로 반영했습니다. 복제본에서 자동 판정과 버전 증가를 실행해 `0.0.7 → 0.1.0`을 확인했으며, 원본 저장소의 버전 파일이나 태그는 변경하지 않았습니다.
