# CCUH 개발 체크리스트

## 목적과 범위

Computer Use가 작업할 앱을 인식하는 부분과, 인식한 앱 안에서 입력이나 클릭 등의 작업이 실패하는 부분을 보완합니다.

기존 자동 수신은 연결 기반으로 유지합니다. 실제 보완 기능은 앱 인식 문제와 앱 내부 작업 실패에 집중합니다. 2026-11-03 사용자 정정에 따라 작업 환경의 사전 관측을 대상 인식보다 먼저 수행하도록 순서를 보완합니다. 전체화면과 모니터 배치를 사용자가 반복 조작하는 시험으로 확장하지 않고, 읽기 전용 관측으로 확인 가능한 정보와 미확인을 구분합니다.

### 백그라운드 간섭의 판정 기준

작업 창 올림과 화면 전환을 금지하는 아래 조건은 background 모드에 적용합니다. 사용자가 명시적으로 선택한 visible 모드에서는 해당 절차에 따라 확인된 작업 창을 표시할 수 있으며, 허용된 표시를 백그라운드 간섭 실패로 계산하지 않습니다. 올바른 대상에만 입력하는 보호와 검증 근거를 구분하는 원칙은 두 모드에 공통입니다.

- 사용자가 다른 앱이나 유튜브를 클릭하고, 화면과 데스크탑을 전환하며, 원하는 곳에 입력하는 것은 정상 사용입니다. 사용자가 선택을 바꾼 사실을 CCUH의 실패로 판단하거나 특정 앱과 입력란을 계속 선택하도록 요구하지 않습니다.
- CCUH가 작업 앱을 임의로 활성화하거나 앞으로 올려 사용자의 화면을 가리고, 앱이나 데스크탑을 강제로 전환하는 경우를 간섭으로 판단합니다. 작업 입력과 클릭은 확인한 대상 안에서 수행해야 하며, 사용자 조작을 에이전트의 작업으로 혼동하지 않습니다.
- 검증은 에이전트가 실제 호출한 동작과 관측된 화면 변화를 대조합니다. 창 올림 호출이 없다는 사실만으로 모든 화면 변화가 없었다고 보장하지 않습니다.
- 실제 동시 타이핑 조건이 확인되지 않았다면 키보드 입력 분리가 검증됐다고 기록하지 않습니다. 매 단계에 같은 입력 대상 유지 질문을 반복하거나, 일반 기능 검증의 완료 조건으로 사용자 타이핑 시험을 추가하지 않습니다.

### 0. 작업 환경의 사전 관측

사용자는 메인 모니터에 전체화면 Chrome을 사용하고 있었으나, 공식 App은 사이드 모니터의 일반 Chrome 창을 반환했습니다. 그 창의 보기 메뉴에 `전체 화면 시작`이 있다는 관측을 사용자 전체 화면의 상태로 해석한 것은 잘못입니다. 사용자 정정 뒤 계산기 Raise는 실행하지 않았고, 열었던 Chrome 메뉴를 취소한 뒤 정책을 background로 돌리고 연결 참조를 정리했습니다.

새 순서는 **환경 관측 → 대상 확정 → 모드 적용 → 실제 동작과 결과 확인**입니다. 사용자는 모니터와 창 배치의 메타데이터만 읽는 별도 수집기의 설계와 구현을 승인했습니다. 실제 클릭과 입력은 기존 공식 Computer Use가 계속 수행하며, 환경 관측이 앱 접근 승인을 이전하거나 실행 엔진을 대체하지 않습니다.

- [x] **0.1. 관측 계약** — 디스플레이 ID와 Quartz 좌표, primary와 배율, 현재 화면의 일반 창 ID/PID/번들 ID/좌표/교차 디스플레이, 앞에 있는 앱의 PID와 번들 ID를 구분합니다. 시스템 primary를 사용자가 지칭한 메인 모니터나 현재 포커스 화면으로 간주하지 않습니다.
- [x] **0.2. 읽기 전용 수집과 경계 검사** — 공개 AppKit/CoreGraphics의 원샷 프로그램과 Node 연결을 구현했습니다. 창 제목, URL, 페이지 본문, AX, 화면 픽셀과 입력 이벤트는 읽지 않습니다. 자동 권한 요청과 앱 활성화도 없습니다. 타입과 컴파일 및 실제 환경 조회 없는 76개 계약 검사를 통과했습니다. 41개 관측 계약, 17개 훅 경계, 13개 격리 빌드 경계와 5개 네이티브 직렬화 검사를 포함하며, 빌드 타임아웃 뒤에는 직접 만든 시험 프로세스와 자식이 종료된 것도 확인했습니다.
- [x] **0.3. 설치본의 실제 자동 관측** — 수정 설치본의 실제 CUA 초기화 호출에서 디스플레이 2개와 현재 화면의 일반 창 16개가 호출 전 문맥으로 자동 전달됐습니다. 일반 도구의 기록 불변과 reset의 `not-requested`도 확인했습니다. 모니터/창 배치의 관측이며 전체화면과 실행 대상의 연결까지 검증한 결과는 아닙니다.
- [ ] **0.4. 실제 대상과의 연결** — OS 창 ID와 CUA의 App/창, Chrome의 프로필/탭 사이의 공식 연결 근거를 확인합니다. 같은 앱이라는 이유만으로 모니터를 연결하지 않습니다. Space와 정확한 전체화면 상태는 현재 수집기의 지원 범위가 아닙니다.

#### 0.4 실제 관측과 미지원 선택 조건

2026-11-03에 공식 메타데이터 초기화, 설치된 순수 부트스트랩과 background 획득을 거쳐 실행 중인 계산기를 읽었습니다. 공식 App 관측은 `Window: "계산기", App: 계산기.` 헤더와 AX 루트의 `ID: main`을 반환했습니다. OS 수집기의 창 ID와 연결하는 필드는 제공되지 않았습니다. 앱 목록은 앱 ID와 실행 상태를, 승인된 브라우저 메타데이터는 확장 인스턴스 ID를 반환했습니다. 이 값을 OS 창 ID나 특정 모니터의 실행 대상으로 바꾸어 해석하지 않습니다. 앱 접근 권한과 macOS 권한이 별도라는 점은 [공식 Computer Use 안내](https://learn.chatgpt.com/docs/computer-use)와 같습니다.

같은 공식 계산기 App에 `displayId: 999999`, `windowId: 999999`를 추가한 `createTarget`을 실제로 호출하자, 기존 설치본은 두 조건을 무시하고 앱과 제목만 비교해 `ready / window-selector-matched`를 반환했습니다. 클릭, 입력, 메뉴 재선택과 Raise는 수행하지 않았습니다. 이는 OS 창 연결 성공이 아니라 JS 옵션의 묵시적 무시 결함을 재현한 결과입니다.

수정본은 허용된 자체 데이터 필드만 복사하고 미지원 선택 필드, 접근자, 심볼과 사용자 정의 옵션 prototype을 App 관측 전에 거부합니다. 공식 App 객체 자체의 prototype과 동일 참조는 유지합니다. 누락된 창 연결을 만들어 주는 수정은 아니므로 **0.4 실제 대상 연결은 미완료로 유지**합니다. 수정을 피하려고 사용자 요청의 모니터나 창 조건을 제거해서 진행하지 않습니다.

이전 생성물에서 22개 경계가 실패하는 재현을 확인했고, 수정 소스와 재생성한 런타임에서는 각각 43개 검사가 통과했습니다. 정상 옵션, null prototype과 frozen 옵션, 같은 공식 App 객체를 사용하는 읽기 경로를 유지했으며 미지원 선택 조건과 접근자 거부 때 앱 읽기, 입력과 클릭이 추가되지 않았습니다. 이 결과는 메모리 App 대역과 생성물 VM 검사이며, 수정 설치본의 실제 CUA 거부 검증과 구분합니다.

이후 v0.7.1 설치본의 두 훅이 trusted인 것을 확인하고 실제 CUA에서 런타임 해시 `4a85cc1982980dbf76793f26b94faeab3503ce8743efcf4c59eb6a8c8e43fee2`와 소스 해시 `9b3652c03f10586c7621102824c062638ca6bd4a43a381991ecec281915ee7f6`의 로드를 확인했습니다. 같은 공식 계산기 App에서 displayId 단독, windowId 단독과 두 필드 동시 요청이 모두 TypeError로 거부됐습니다. 정상 앱/제목 대상은 `ready / window-selector-matched`, 재선택 0회를 유지했습니다. 클릭, 입력, Raise와 화면 전환을 요청하지 않았고 끝에 연결 참조를 reset했습니다. 이는 선택 조건의 묵시적 무시 수정 검증이며 OS 창 연결의 성공 근거가 아닙니다.

#### 0.4 브라우저 내부 관계와 창 상태

macOS 네이티브 App 경로에서는 현재 제공된 공식 getApp이 앱 이름, 경로 또는 번들 ID만 받습니다. 창 ID 선택과 listWindows는 현재 도구 문서에서 Linux/Windows용이며, 이를 macOS에서 같은 기능으로 시험하지 않습니다. 공식 문서와 현재 제공된 API에서 공통 OS 창 식별자를 확보하지 못했으므로 이 부분은 **진행 중 구현이 아닌 외부 API 의존으로 막힌 미완료**입니다. 같은 앱 조회를 반복해 완료로 바꾸지 않습니다.

2026-11-04에 v0.8.16 기준으로 이 의존성을 다시 검토했습니다. 현재 소스와 생성물의 대상 옵션 경계 검사 43개가 각각 통과했고, 미지원 창과 모니터 선택 조건을 거부할 때 입력과 클릭 및 getter 실행은 0회였습니다. 이는 메모리 App과 VM 검사이며 네이티브 창 연결 성공의 근거가 아닙니다. 기존 수집기에는 OS 창 ID가 있고 공식 App에는 앱명과 창 제목만 있어 공통 식별자가 없습니다. 제목, 좌표나 같은 앱이라는 사실로 연결을 추정하는 resolver는 추가하지 않았습니다. macOS 공식 창 핸들 또는 OS 창 ID 연결 기능이 제공되면 재개하며, 그동안 0.4는 미완료로 유지하고 독립적으로 진행 가능한 다음 항목을 확인합니다.

브라우저의 공식 management 기능에서는 별도의 직접 관계를 확인했습니다. [Chrome Tab.windowId](https://developer.chrome.com/docs/extensions/reference/api/tabs#type-Tab)는 탭이 속한 Chrome 창을 가리키며, [Window.state](https://developer.chrome.com/docs/extensions/reference/api/windows#type-Window)는 해당 브라우저 창이 보고하는 fullscreen 등의 상태입니다. 실제 CUA 조회에서 선택된 같은 Chrome 연결에 일반 창 1개와 fullscreen 창 1개가 함께 있었고, 요청한 공개 PR 탭의 Chrome windowId를 얻었습니다. 이때 창 이동, 활성화와 페이지 본문 조회는 수행하지 않았습니다. CUA의 opaque providerTabId도 반환됐지만 해독하거나 Chrome numeric ID로 변환하지 않았습니다.

`src/recognition/browser.ts`의 읽기 전용 관측은 선택한 공식 Browser와 실제 management가 반환한 numeric 탭 ID만 받습니다. tabs.get, windows.get와 탭 재확인에서 반환 ID와 창 관계를 대조합니다. 반환에는 같은 브라우저 세션의 탭/창 ID, Chrome의 창 상태와 선택적 bounds 및 관측 시각만 남기며 URL, 제목과 원문 오류는 포함하지 않습니다. 메타데이터가 없거나 탭이 이동하면 미확인으로 종료하고 폴백과 반복을 하지 않습니다.

이 값은 **Chrome 내부 관계의 관측**입니다. OS 창, 기존 CUA Tab 객체의 opaque ID, 디스플레이와 Space 연결을 제공하지 않습니다. Chrome bounds는 해당 API의 pixel 좌표이며 Quartz 좌표와 단위나 원점이 동일하다고 보장하지 않습니다. 탭 재확인 뒤에도 창 배치는 바뀔 수 있는 비원자적 관측입니다. 기존 CUA Tab을 이 값으로 재연결하거나 브라우저 하나의 상태를 전체 사용자 환경의 상태로 일반화하지 않습니다. **0.4 전체는 미완료로 유지합니다.**

수정 소스와 생성 런타임의 브라우저 경계 검사 각각 78개, 순수 부트스트랩과 도구 제외 7개 및 기존 대상 옵션 검사 각각 43개를 확인했습니다. 모두 메모리 대역과 VM 검사이며 실제 브라우저나 OS를 조회하지 않았습니다. 실제 management의 읽기 경로 관측과, 수정 설치본 도우미가 자동 로드된 뒤의 실행 검증은 별도 근거로 구분합니다. Chrome ID를 다른 호출이나 브라우저 재시작 뒤에 계속 재사용하지 않으며, browserId 자체를 OS 식별자나 재시작을 넘는 세션 증명으로 취급하지 않습니다.

#### 브라우저 관측의 지역 실행 분리

브라우저 읽기에도 네이티브 가드 전체를 로드하고 전역 도우미와 기록을 등록하던 경로를 분리했습니다. 새 `CCUH_BROWSER_WINDOW_V1` 표식은 기존 Browser 바인딩의 단일 식별자와 management에서 실제 얻은 numeric 탭 ID만 받습니다. 정확한 한 줄만 치환하며 일반 JS, 추가 실행 코드, reset과 다른 도구는 그대로 둡니다. 생성물은 같은 browser.ts를 포함하는 약 6KB 지역 async 함수이며 기존 약 58KB 네이티브 런타임의 바이트는 유지합니다.

한 셀 안에서 관측 모듈을 정의하고 기존 Browser를 읽어 세 메타데이터 API를 호출한 뒤 결과와 생성물 해시만 출력합니다. 전역 ccuh와 bootstrap 기록을 등록하지 않고 native 가드, mode와 앱 획득을 로드하지 않습니다. 기존 native 표식과 API는 호환성을 위해 유지합니다. 두 경로는 제한된 파일 읽기, UTF-8와 구문 및 소스/바이트 해시 검사를 공유합니다. 빌더의 --check는 두 생성물을 모두 대조합니다.

VM 경계 검사에서 지역 변수와 같은 이름의 caller 바인딩, 바인딩 누락, getter 미실행, ID 검증, API 오류와 탭 이동 및 전역 속성 불변을 확인했습니다. 예약 이름 일부가 느슨한 구문 검사에서 허용되는 실패를 재현한 뒤 strict-mode 파싱으로 수정했으며 새 10개 검사 그룹이 통과했습니다. 기존 브라우저 경계 각각 78개와 native 로더 7개 및 대상 옵션 각각 43개도 통과했습니다. 이 검사는 메모리 API 대역과 VM을 사용했으며 실제 환경 조회를 포함하지 않습니다.

호스트 검토와 앱 접근 승인은 유지하며 PermissionRequest 승인 훅을 추가하지 않습니다. 이 작은 경로를 브라우저 읽기의 처음부터 선택하고, 거절되면 다른 로더나 직접 호출로 대체하지 않습니다. 코드 변경에 따른 설치 훅 신뢰 검토와 매 관측의 별도 런타임 허용을 구분합니다. 네이티브 OS 창 연결은 여전히 미완료입니다.

관측은 유효한 CUA PreToolUse JS와 세션/호출 식별자를 확인한 뒤에만 실행합니다. 호출 후와 reset, 일반 도구 및 모듈 import에서는 실행하지 않습니다. 훅은 각 호출의 문맥에 결과를 전달하며 기존 receipt에는 상태, 고정 실패 사유, 관측 해시와 시각만 남깁니다. ### 연결된 대상의 내부 처리 보완

사용자의 후속 요청에 따라 자동 창 연결은 미해결로 유지하고, 이미 연결된 대상의 오인식과 입력 실패 보완을 우선합니다. 이 범위의 수정과 검증은 아래의 자동 창 재선택 항목을 통과한 것으로 계산하지 않습니다.

2026-11-03에 공개 도우미 API로 네 가지 결함을 재현하고 수정했습니다.

- `Selected text`에 포함된 숫자 행이 실제 입력란으로 처리되거나, 정상 입력란의 `Selected` 요약이 중복 필드로 계산됐습니다. 기존 모달 판정의 선택 요약 분리 로직을 공통 순수 모듈로 추출해 트리만 조회하며, 요약 행의 원본 일치도 검사합니다.
- 중복 ID를 가진 행 중 하나가 추가 ID 문구로 모호하면 그 행을 제외하고 나머지 필드에 썼습니다. 요청 ID를 언급한 모든 실제 행으로 유일성을 먼저 판정합니다.

- `withTarget`에 함수가 아닌 작업을 넘기면 앱 관측 후 예외가 발생했습니다. 관측 전에 잘못된 콜백을 차단합니다.

#### 1번 실사용 검증과 보완 기록

첫 독립 요청은 포커스 유지 근거 부족으로 실행 전 검토에서 거절됐습니다. 공식 macOS 백그라운드 지원과 과거 같은 경로의 실제 기록을 대조한 재검토에서는 허용됐으나, 요청한 창 메뉴 대신 다른 메뉴가 관측돼 대상 클릭 없이 중단했습니다. 사용자는 그 실행 동안 다른 앱의 화면과 입력 대상이 유지됐다고 확인했습니다. 메뉴는 노출된 공식 Cancel 동작으로 정리하고 소멸을 확인했습니다. 읽은 참조에 임의의 숫자 보정을 적용하거나 전경 키로 우회하지 않았습니다.

메뉴 열기 직전 같은 앱과 창의 전체 상태를 1회 재확인하고 최신의 유일한 참조만 사용하는 보완을 작성했습니다. 참조 변경, 헤더 변경과 읽기 실패 등을 다룬 18개 대역 시나리오는 원본과 생성물에서 각각 통과했습니다. 타입, 생성물 일치와 구문 및 포맷 검사도 통과했습니다. 이 결과를 실제 재선택 성공으로 계산하지 않습니다.

이 수정본의 새 대화에서는 공식 App이 제목 없는 표준 창과 창 메뉴를 반환했습니다. 기존 `reselect` 콜백 경로는 `unknown / window-unobserved`에서 시도 0회로 차단됐습니다. 이를 보완하는 `windowMenu` 고정 경로를 추가했습니다. 같은 앱이 확인되고 실제 메뉴가 있을 때만 메뉴 탐색을 1회 허용하며, 원래 목표 제목의 재관측이 일치해야 작업 콜백이 실행됩니다. 임의 콜백을 unknown에서 실행하거나 창 선택 조건을 없애지 않습니다. 신규 통합 15개, 잘못된 옵션 10개와 다른 판정 및 비교 근거 16개 경계가 대역에서 통과했습니다. 최종 수정본의 실제 UI 경로는 별도로 확인해야 합니다.

그 다음 독립 대화에서는 CCUH를 요청에 넣지 않아도 `windowMenu`를 구성했고, 제목 없는 창에서 `ready / window-selector-matched`, `recoveryAttempts: 1`, `recovered: true`까지 실행됐습니다. 실행 런타임은 `c7a67a3f…`, 소스는 `afccc853…`였습니다. 그러나 사용자는 다른 화면에서 조억만 창이 VS Code 위로 올라왔다고 확인했습니다. 이 결과는 대상 발견 성공과 작업 공간 유지 실패로 분리하며 전체 항목은 미통과입니다. 연결 참조만 js_reset으로 정리했고 사용자의 창을 임의로 닫거나 다시 배치하지 않았습니다.

창 메뉴 항목의 `makeKeyAndOrderFront:`는 창을 앞으로 올리는 동작입니다. 이를 반영해 `allowWindowRaise`를 기본 `false`로 추가했습니다. 기본값이나 명시한 `false`에서는 재선택 경로가 실행되지 않고, 가능한 복구를 차단한 경우 시도 0회와 `recoveryBlockedReason: window-raise-not-authorized`를 반환합니다. 직접 메뉴 함수를 호출해도 동일한 효과 선언이 없으면 조회와 클릭 없이 중단합니다. 이미 맞는 대상의 정상 작업은 유지합니다. `true`는 사용자 동의나 앱 승인을 증명하지 않으며, 작업 공간 유지 요청에서는 설정하지 않습니다.

새 기본 안전 시나리오 22개와 잘못된 효과 옵션 9개가 대역에서 통과했습니다. 기존 허용 경로 검사는 가상의 명시적 허용 조건을 설정해 보존했으며, 현재 사용자 조건에서 창을 올리는 추가 실제 시험은 하지 않습니다. 이 안전 수정도 창을 올리지 않는 대상 지정 기능의 구현 완료나 실제 포커스 보존 성공으로 설명하지 않습니다.

기본 차단본은 생성 런타임에서도 같은 31개 검사를 통과했습니다. 원본과 설치본의 실행 파일 13개가 같고 두 훅이 trusted인 것을 확인했습니다. 실제 Computer Use의 공식 카카오톡 App에서도 다른 창이 연결된 상태에서 `prepareTarget`이 `blocked`, `recoveryAttempts: 0`, `recoveryBlockedReason: window-raise-not-authorized`를 반환했습니다. 이 검사는 창 선택을 실행하지 않는 차단 확인입니다. 실행 런타임 해시는 `c0b83484…`, 소스 해시는 `c47a9e06…`이며 이후 js_reset으로 연결 참조를 정리했습니다. 창을 뒤에 둔 채 지정하는 원래 항목은 여전히 미완료입니다.

##### 실제 접근성 트리의 대체 경로 확인

같은 날 공식 Computer Use로 카카오톡에 연결하고 설치된 도우미의 런타임 `c0b83484…`, 소스 `c47a9e06…`를 확인했습니다. 같은 승인 App의 전체 AX 상태를 앱 범위 가드 안에서 읽어, 다른 대화창의 실제 요소가 함께 제공되는지 조사했습니다. 반환된 네이티브 최상위 창 컨테이너는 메인 창 1개였으며, 요청한 조억만의 창 헤더와 창 컨테이너는 모두 없었습니다. 이름은 채팅 목록에만 있었고, 목록 항목을 대화창 바인딩으로 취급하지 않았습니다.

이 조회의 `executed / app-selector-matched`는 메인 앱 트리를 읽었다는 뜻이며, 요청한 대화창 연결이나 포커스 보존 성공을 뜻하지 않습니다. 메뉴 선택, 클릭, 입력과 재선택은 모두 0회였고, 이후 공식 `js_reset`으로 참조를 정리했습니다. 이번 상태에서는 다른 창의 요소를 직접 사용하는 대안도 확인되지 않았습니다. 카카오톡에 해당 창이 실제로 열려 있는지, 모든 앱의 AX가 단일 창인지까지 증명한 결과는 아닙니다. 코드나 설치본을 바꾸지 않았으며 원래 목표는 미완료입니다.

##### 공식 기능 요청안

아래는 검토 가능한 초안이며 외부에 게시하거나 전송하지 않았습니다. API 이름은 제안하지 않고 필요한 동작을 명시합니다.

**Title: macOS Computer Use: bind a native window without activation or reordering**

Computer Use can operate macOS apps in the background, but its currently documented API binds an app by name, path, or bundle identifier. The window-ID form of `getApp` and `listWindows` are documented for Linux and Windows only.

When an app has several native windows, the approved app binding may observe a different window from the task target. In our KakaoTalk test, selecting the intended conversation from the app's Window menu reached the right title but raised that window over the user's editor on another display. Preserved typing alone did not establish preserved window order.

Please provide a supported way to enumerate and bind an individual macOS native window within an already approved app. Binding and background operations should preserve the user's active app, keyboard input target, window order, and Spaces on every display. The interface should distinguish duplicate titles, report closed or recreated windows as invalid instead of silently retargeting, and retain existing app-approval boundaries. Unsupported apps or operations should report that limitation before changing the user's workspace.

### 1번 정확한 로딩과 설치본

로컬 플러그인을 공식 관리 명령으로 갱신하고 실행 소스, 진입점, 스킬, 생성물과 훅 설정 13개 파일의 바이트 일치를 확인했습니다. 사용자가 Codex App에서 변경된 PreToolUse와 PostToolUse 두 훅을 검토했고 공식 조회에서 trusted를 확인했습니다. 신뢰 기록을 대신 수정하지 않았습니다.

정상 초기 App 접근과 승인 이후, CUA 코드 전체가 `// CCUH_BOOTSTRAP_V1`과 정확히 같은 경우에만 훅이 고정된 설치 런타임을 읽어 넣습니다. 다른 JS, 표식에 내용이나 공백을 붙인 경우, 앱 접근, js_reset과 다른 도구는 치환하지 않습니다. 런타임 누락, 잘못된 UTF-8과 BOM, 크기 초과 또는 구문 오류는 표식만 고정 이유로 차단합니다. 실제 App 접근 권한과 일반 작업 호출의 승인은 그대로 유지합니다. 입력 교체 형식은 [공식 Hooks 문서](https://learn.chatgpt.com/docs/hooks#pretooluse)를 확인했습니다.

Codex App 번들 `0.166.0-alpha.5.1`의 실제 CUA에서 js_reset과 정상 App 초기화 후 표식만 보냈습니다. 최종 로더의 반환은 ready, loaded였고 설치 파일의 런타임 해시 `441780c3…`와 소스 해시 `7840ea24…`가 일치했습니다. 연결된 Pre와 Post의 세션 및 호출 해시가 같았으며, Post에서 관측한 코드 해시는 원래 표식이 아니라 최종 치환 코드의 SHA256 `bb03166f…`과 같았습니다. 동일한 설치 모듈에서 코드를 다시 구성한 해시도 직접 대조했습니다. 이 경로에서 모델은 런타임 본문을 전사하지 않았습니다.

실제 REPL 검증에서는 VM 검사로 찾지 못한 수명 문제 두 가지가 드러났습니다. 조건문 안에서 선언한 helper는 다음 셀에 등록되지 않았고, 최상위 선언만 추가한 판에서는 반복 호출 때 기존 helper 대신 새 helper가 만들어졌습니다. 표식의 성공 반환과 다음 셀의 변수 유지가 별개임을 확인했습니다. 앱 입력 없이 일반 셀 변수와 JS global property를 대조하고, 전용 속성의 셀 간 유지와 실제 reset 시 삭제를 먼저 시험했습니다.

### 4번 제어된 네이티브 통합 검증

저장소 밖의 일회용 AppKit 시험 앱에서 정상 `cua.getApp` 승인과 같은 공식 App 객체를 사용했습니다. 공식 메소드와 CUA 엔진을 래핑하지 않았고 관측값도 위조하지 않았습니다. 사용자는 앱 접근을 직접 승인했습니다. 첫 준비 구간의 창 활성화는 사용자가 시험 창도 직접 클릭했다고 확인했으므로 이후 별도 프로세스의 실행 구간과 분리했습니다.

초기 시험 앱이 입력란 ID를 부모와 자식에 중복 노출했을 때 CCUH는 쓰기 전에 차단했습니다. 시험 앱의 공개 AX 노출을 단일 텍스트 필드로 고친 뒤에도, 입력을 무시하고 즉시 재생성하는 조건에서는 공식 `App.setValue`가 예외를 반환했습니다. helper는 네이티브 setter 1회에서 중단했습니다. 정확한 SDK 내부 원인을 확정하거나 이 결과를 정상 반환 후 재시도로 바꾸어 보고하지 않습니다.

| `failed`  | 명시적으로 제공된 접근 거부, 앱 또는 창 없음, 참조 무효화, 비교 가능한 앱 또는 창 선택 조건 불일치  |
| `matched` | 요청한 선택 조건과 관측 값의 일치. 앱 범위와 창 범위를 구분하고 비교 근거를 `basis`에 남김          |
| `unknown` | 다른 요청, 오래됐거나 미래 시각인 관측, 불충분하거나 모호한 대상, 비교할 수 없는 식별자와 형식 오류 |

명시적 실패 종류는 CCUH 내부의 정규화 계약입니다. 공식 도구가 이 이름의 오류 코드를 반환한다는 뜻이 아니며, 일반 예외의 문구만 보고 접근 거부나 대상 없음을 추정하지 않습니다. 연결부는 실제 근거가 확인된 경우에만 해당 종류를 제공해야 합니다.

같은 요청인지와 관측 시각을 먼저 확인합니다. `nowMs`와 `maxAgeMs`는 호출자가 명시하며 기본 허용 시간을 만들지 않았습니다. 모호한 관측으로 특정 대상을 확정하지 않고, 비교 가능한 앱 조건이 다르면 창 비교를 진행하지 않습니다. 창 ID는 앱 식별자가 bundle ID이고 식별자 namespace도 같을 때만 비교합니다. 앱 표시명과 창 제목은 NFC로 정규화해 비교하되, ID와 제목을 서로 대신하지 않습니다.

`basis: ['app-name', 'window-title']`의 일치는 표시명과 제목 조건이 같다는 뜻입니다. 동일한 안정 창 ID, 앱 접근 승인이나 후속 입력의 성공을 보장하지 않습니다. 관측 후 대상이 바뀌는 문제와 실제 작업 전 재확인은 2.3에서 다룹니다.

### 2.2 가드의 고정 실패 단계

v0.8.3의 첫 네이티브 읽기 가드가 `unclassified-error`로 중단됐지만 이후 같은 App의 읽기와 가드는 통과했습니다. 기존 catch 하나가 AX 읽기, 시각 생성, 헤더 판독과 분류 예외를 모두 같은 사유로 바꾸고, 작업 중복 차단에도 같은 사유를 사용해 발생 단계를 구분할 수 없었습니다. 이번 수정은 다음 실패를 진단할 수 있도록 unknown 인식 결과에 선택 필드 `failureStage`를 추가합니다. 당시 최초 오류의 원인을 소급해서 확정하는 수정은 아닙니다.

### 2.3 연결 계약

지원하는 CUA 호출의 PreToolUse와 PostToolUse에서 고정된 `additionalContext`를 제공합니다. 등록된 `ccuh:ccuh` 스킬은 공식 App 객체와 의도한 앱 표시명 및 창 제목으로 대상 바인딩을 만듭니다. 훅이 UI 원문을 해석해 대상을 추정하거나 접근 허용을 결정하지는 않습니다.

`createTarget()`은 의도한 조건을 REPL 메모리에 유지합니다. `withTarget()`은 같은 App 객체의 전체 최신 상태를 읽고 2.2 분류기를 적용한 뒤, 조건이 맞을 때만 작업 콜백을 한 번 실행합니다. 전달된 최신 상태에서 인덱스를 찾아야 하며, 다른 객체나 이전 상태에서 얻은 인덱스를 재사용하지 않습니다.

창 조건만 다르고 공식 재선택 경로가 주어졌다면 그 경로를 한 번 호출하고 다시 관측합니다. `selectWindowFromMenu()`는 같은 앱의 실제 메뉴 모음과 popup 라벨, 유일한 제목 및 표준 창 항목을 확인합니다. 클릭이 반환됐다는 것만으로 성공하지 않으며, 가드의 새 관측이 일치해야 콜백을 실행합니다. 앱 불일치, 잘못된 헤더, 접근 예외와 불확실한 대상은 중단합니다.

`prepareTarget()`의 결과는 그 시점의 검사 요약입니다. 이후 `withTarget()`은 다시 검사합니다. `executed`는 콜백이 반환됐다는 뜻이며 저장이나 전송의 성공 판정이 아닙니다. 콜백이 정상 반환되면 대상을 다시 읽습니다. 대상이 바뀌거나 콜백에서 예외가 발생해도 이미 시도한 작업을 반복하지 않습니다. 같은 App 객체의 가드 작업이 겹치면 후속 호출을 중단합니다.

### 2.3 백그라운드 재선택 제한의 구분

2026-11-03에 제공된 공식 API와 [공식 Computer Use 안내](https://learn.chatgpt.com/docs/computer-use)를 다시 대조했습니다. 공개 안내는 macOS 백그라운드 작업을 설명하지만, 현재 제공된 macOS App API에는 기존 승인 App의 다른 창을 창 올림 없이 바인딩하는 메서드가 없습니다. windowId 선택과 listWindows는 제공 도구 문서에서 Linux/Windows용이며, 기존 창 메뉴의 makeKeyAndOrderFront 경로를 백그라운드 무간섭 선택으로 사용하지 않습니다. 0.4와 실제 백그라운드 재선택은 미완료로 유지합니다.

현재 가드가 지원하지 않는 재선택을 단순 창 올림 권한 부족으로 안내하지 않도록 summary의 `recoveryBlockedReason`을 구분합니다. 새 동작은 작업 전 같은 App의 유효한 관측에서 필수 창 제목이 다르거나 없을 때만 적용합니다.

| 모드와 조건                                        | 반환 사유                            | 재선택 시도 |
| -------------------------------------------------- | ------------------------------------ | ----------- |
| background의 같은 앱 창 불일치 또는 필수 제목 없음 | `background-reselection-unsupported` | 0회         |
| visible의 복구 가능 조건에서 창 올림 명시적 금지   | `window-raise-not-authorized`        | 0회         |

background 사유는 재선택 경로가 없거나 allowWindowRaise가 true여도 동일합니다. 공통 지침에는 제한을 바로 알리고 중단하고, 같은 요청에서 사용자에게 반복해서 창을 올리도록 요구하거나 앱 재획득, 다른 엔진과 자동 visible 전환으로 진행하지 않도록 명시했습니다. 사용자가 나중에 새로 visible을 선택하는 것은 별도 정책 선택입니다. 이 수정은 창을 선택하는 API나 새로운 권한을 추가하지 않습니다.

기존 recognition과 정상 결과 형태는 유지합니다. 앱 불일치, AX 읽기 실패, 잘못된 헤더와 다른 unknown 결과에 재선택 미지원 사유를 붙이지 않습니다. visible의 custom reselect가 창 제목 미관측 상태에서 새로 실행되지 않도록 기존 메뉴 경로 조건도 보존합니다. 초안 교체의 target-unconfirmed 결과와 모든 쓰기 상한은 그대로입니다.

`withVerifiedTarget(target, action, verify)`는 같은 공식 App의 대상 확인 뒤 작업을 한 번 실행하고, 예외가 나도 최신 상태를 다시 읽습니다. 호출 결과 `invocation: returned/threw`와 관측 결과 `confirmed/not-observed/unknown`을 별도로 반환합니다. 기존 `withTarget`의 동작은 유지합니다.

검증기는 같은 대상의 변경된 전체 AX 스냅샷 `before/after`만 받아 요청한 변화가 확인되면 true, 관측되지 않으면 false, 판단이 어려우면 unknown을 반환합니다. 동일한 스냅샷은 검증기를 호출하지 않고 `no-observable-change`로 남깁니다. 작업 후 대상이 달라졌거나 관측할 수 없으면 재선택하지 않고 unknown으로 중단합니다. 검증기 오류도 unknown입니다. 자동 재시도와 반복 조회는 없으며 원문과 예외 본문을 로그에 저장하지 않습니다.

`checked`는 확인 절차를 수행했다는 뜻이며 성공 판정이 아닙니다. `not-observed`도 해당 관측에서 변화가 확인되지 않았다는 뜻으로, 영구 실패나 재시도 허용을 의미하지 않습니다. 전송 검증은 이전부터 있던 같은 메시지나 입력란 비움과 구분되는 새 근거가 필요합니다. 특정 창을 고정한 binding은 그 창의 소멸이나 교체 뒤에 같은 대상이라고 확정할 수 없습니다. 모달 취소는 의도에 맞는 앱 범위 binding과 `verifyModalDismissal`로 명시한 부모 복귀를 따로 확인합니다.

격리된 앱 대역으로 21개 시나리오를 개발 소스와 생성 JavaScript에서 각각 실행했습니다. 변화 반영, 반환됐지만 변화 없음, 관련 없는 변화, 반영 후 예외, 반영 전 예외, 대상 변경과 조회 실패, 검증기 오류, 동시/중첩 호출 차단, 제목 없는 시트의 앱 범위 처리, 기존 API 동작과 작업/재선택 횟수 제한이 통과했습니다. 빌더는 새 내부 모듈을 포함하며 허용하지 않은 의존성 11종을 거부했습니다. 이 검사는 실제 앱이나 Computer Use를 호출하지 않았으며 실제 연동 근거로 확대하지 않습니다. 영구 테스트 파일이나 추가 패키지는 만들지 않았습니다.

### 3.1 실제 Computer Use 검증과 발견한 한계

공식 TextEdit App 객체를 얻고 설치된 도우미를 CUA REPL에 로드해, 새로 만든 시험 문서에서 다음을 확인했습니다. 별도 UI 엔진이나 MCP 작업 도구를 선택하지 않았으며 실제 Pre/Post 지침이 호출에 전달됐습니다.

| 실제 시험                                     | 호출과 관측 결과                                                                          |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 본문 A에서 B로 변경                           | 입력1회, returned와 confirmed                                                             |
| 볼드체 체크상자0에서1로 변경                  | 클릭1회, returned와 confirmed                                                             |

| 본문 B에서 C로 변경한 뒤 의도적으로 예외 발생 | 입력1회, threw와 AX 기준 confirmed. 실제 CUA API의 자연 발생 예외가 아닌 제어된 오류 주입 |

최초 문서 입력에서 AX 값의 표기와 포커스 요약 행을 검증기가 제대로 구분하지 못했을 때는 unknown을 반환했습니다. 실제 입력란 한 행만 비교하도록 시험 검증기를 바로잡았습니다. 문서 제목이 `.rtf`를 포함하도록 바뀌었을 때도 입력 전에 차단했으며 그 시도의 입력 횟수는0이었습니다. 관측한 새 제목을 기준으로 의도한 시험 문서를 다시 선택했습니다.

- **로딩 정확성:** 실행 측은 최초 도우미 전사에서 setter 기능 검사를 누락했고 UI 작업 전에 원본을 다시 로드했다고 보고했습니다. 파일의 선언된 `sourceHash` 값이 같아도 REPL에 전달한 코드의 바이트가 같다는 증거는 아닙니다. 모델이 긴 코드를 옮기는 과정의 정확성을 별도로 보장하거나 검증해야 합니다.
- **설치본 반영:** 현재 소스의 필드 선택 수정이 설치 캐시에 없습니다. 최신 소스 검사와 실제 설치본 동작을 합쳐 현재 배포물 전체가 통과했다고 보고하지 않습니다.
- **실제 앱 작업 완료:** TextEdit 종료 효과가 확인되지 않은 경우와 카카오톡 메뉴 관측 및 대상 선택 실패가 남았습니다. 감지 후 중단한 사실과 요청한 작업이 완료됐다는 사실을 구분합니다.
- **일반 앱의 자연 발생 재시도:** 실사용 2는 미검증입니다. 의도적인 무반영 주입이나 대역의 새 참조를 일반 앱의 자연 발생 실패 복구로 바꾸어 보고하지 않습니다. 3.3.3의 제어된 실제 앱 통합 검증은 위 후속 결과와 구분합니다.

## 공통 제약과 진행 방법

- Computer Use의 앱 접근 제한과 필요한 승인을 유지합니다. 공식 앱 핸들을 별도 AX 엔진의 권한으로 이전하지 않습니다.
- 사용자의 입력 대상을 임의로 전환하지 않습니다. 앱 인식 실패를 전경 앱 강제 활성화나 전역 키보드 입력으로 우회하지 않습니다.
- 대상이 모호하거나 접근이 거부되면 중단합니다. 막힌 지점과 필요한 다음 행동을 즉시 알리고, 같은 실패를 말없이 반복하지 않습니다.
- 각 항목은 개발, 검증, 리팩토링과 재검증을 마친 뒤 실제 결과로 완료 표시합니다. 합성 입력 검사나 과거 버전의 결과를 현재 기능의 완료로 옮기지 않습니다.
- 사용자 도움은 실제 실패 당시 상태 확인이나 본인의 승인처럼 자동화할 수 없는 경우에만 요청합니다.

## 기존 검증의 위치

호출 시작만 기록했던 수신기와 다른 도구 제외의 이전 근거는 Git 이력에 있습니다. 현재 반환 관측의 근거와 한계는 위 1.3 기록에 있으며, `~/.codex/ccuh/receiver/`의 메타데이터는 앱 작업의 성공 증거가 아닙니다.

계산기의 기존 허용과 체스 요청 취소는 공식 앱 접근 경계의 검증 기록입니다. 앱 인식 오류나 입력과 클릭 실패의 복구가 구현됐다는 의미로 사용하지 않습니다. 포커스 관측기와 그 CI 검사는 이번 개발 범위에서 제거했습니다.

새 결과는 해당 항목 아래에 검증한 소스와 설치본, 실제 실패, 조치와 결과, 남은 조건을 짧게 기록합니다. 이 파일을 유일한 진행표로 유지합니다.

## 릴리스 버전 판정

`main`의 검증된 커밋을 기준으로 현재 메타데이터 버전의 정확한 태그부터 새 커밋 전체를 분석합니다. 과거 리셋 전의 높은 버전 태그나 마지막 병합 제목만으로 증가 폭을 결정하지 않습니다. 기준 태그가 없거나 현재 커밋의 조상이 아니면 자동 판정을 중단합니다.

- `feat:`는 minor, `!` 표기와 `BREAKING CHANGE:` 또는 `BREAKING-CHANGE:` footer는 major로 판정합니다. 일반 병합 제목에도 명시적인 breaking footer가 있으면 major입니다.
- `fix:`와 나머지 변경은 기존 정책대로 patch를 발행합니다. 여러 종류가 섞이면 major, minor, patch 순으로 가장 큰 증가 폭을 한 번 적용합니다.
- 기본 입력은 `auto`이며 수동 실행의 patch, minor와 major 선택은 명시적인 재정의로 유지합니다. 최초 `0.0.0` 발행과 기존 릴리스 재실행 및 `repair_tag` 경로도 유지합니다.
- 일반 병합에서는 내부 기능 커밋까지 읽습니다. squash로 합칠 때는 기능을 나타내는 PR 제목의 `feat:`를 유지해야 합니다. 본문의 단순 `feat:` 예문으로 기능 추가를 추정하지 않습니다.

판정 표기는 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)을 참고하며, 다른 종류의 patch 발행은 CCUH의 기존 정책입니다. 예를 들어 기준 버전이 `0.0.6`이고 그 뒤에 `feat`가 있으면 다음 버전은 `0.1.0`입니다. 이미 발행한 태그를 이동하거나 덮어쓰지는 않습니다.

임시 Git 저장소 9개에서 커밋 판정, 일반 병합 내부의 기능, 우선순위, 버전 파일 동기화, 기준 태그 오류, 최초 발행과 재실행 및 재공개 분기 등 45건을 확인했습니다. 실제 워크플로 실행 블록의 셸 문법도 검사했습니다. 원격 푸시나 GitHub Release 발행은 실행하지 않았으며 이 변경은 `main` 반영 이후 적용됩니다.

추가로 검사 시점의 로컬 `origin/main` 스냅샷을 별도 저장소에 복제하고 이번 변경을 `feat`로 반영했습니다. 복제본에서 자동 판정과 버전 증가를 실행해 `0.0.7 → 0.1.0`을 확인했으며, 원본 저장소의 버전 파일이나 태그는 변경하지 않았습니다.
